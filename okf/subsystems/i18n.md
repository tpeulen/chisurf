# Purpose

ChiSurf's user-facing text lives on three surfaces: the data-driven
`*.view.json` (AutoForm) and `manifest.json` plugin specs, the runtime-loaded
`.ui` forms, and imperative GUI calls (`QMessageBox`, window titles,
custom-section labels). This subsystem makes the **data-driven + `.ui`** surfaces
translatable from a single seam, plus imperative strings that are explicitly
wrapped in `core.i18n.tr(...)`, and ships the kit that extracts, compiles, and
loads catalogues. English is the canonical source language.

# Design

**Qt-free core seam.** `chisurf/core/i18n.py` exposes `tr(text, context="chisurf")`
that defaults to the **identity** function and holds a swappable backend. The
core/server path stays import-clean of any GUI toolkit (the same rule that keeps
[/subsystems/core.md](/subsystems/core.md) and `core/dataspec` Qt-free); the GUI
binds a real backend at startup. `get_locale()`/`set_locale()` read/write the
`gui.language` setting (two-letter code; default `en`).

**GUI bootstrap.** `chisurf/gui/i18n.py:install_translation()` is called in
`get_app()` right after the `QApplication` is created and **before** any window
or `.ui` is loaded (Qt only translates lookups made after install). It binds
`QCoreApplication.translate` as the core backend and installs a `QTranslator`
for `chisurf/gui/i18n/chisurf_<code>.qm`. Because `.ui` loading is runtime `uic`
(see [/subsystems/gui-autoform.md](/subsystems/gui-autoform.md)), every `.ui`
string is localized for free once the translator is installed.

**Language pickers.** `gui/widgets/language_selector.py` hosts the two reusable
pickers — a labelled combo (`LanguageSelector`, used in Settings) and a compact
toolbar flag-dropdown (`LanguageFlagSwitcher`, used in the ribbon corner). Both
discover locales from the shipped `.qm` catalogues, persist + live-apply through a
shared helper, and re-sync via the app-wide `language_notifier`. Flags are
**painted `QIcon`s** built by `gui/i18n.py:language_flag_icon` (a small QPainter
recipe per locale — striped tricolours, a Union Jack for `en`, disc/star for
`ja`/`zh`, a two-letter pill fallback), **not** regional-indicator emoji: emoji
flags render unreliably in Qt menus/buttons (many font stacks show the two letters
in dotted boxes), so the emoji `language_flag` is kept only for tooltips. The icons
are cached by `(code, height)`.

**Live switching.** `apply_language(code)` swaps the installed `QTranslator` and
emits `language_notifier`. Widgets built *after* the swap render in the new
language automatically; **already-open windows do not** — Qt binds `.ui` text at
build time. The main window closes that gap on the notifier: it re-applies the
current translation to its live menus/actions/labels in place via
`gui/retranslate.py:retranslate_from_ui` (parses the form's `.ui` XML,
re-translates each string through the installed translator, writes it back onto
the live child by `objectName` — no widget is re-instantiated, so state and signal
connections survive), then rebuilds the ribbon so the top navigation follows. This
shim exists only because of the runtime `.ui` forms; AutoForm `view.json` UI
retranslates for free on its next build, which is one motivation for retiring the
`.ui` layer ([INC-13](/specs/assessment.md#inc-13)).

**Central localization seams** (all route through `core.i18n.tr`):

- `core/dataspec/__init__.py:_section_from_dict` — every text-bearing field of a
  `view.json` section (title, label, description, suffix, placeholder, add/remove
  labels, axis labels, nested item/button/column text). One choke point → all
  view specs.
- `core/dataspec/rpc.py` — RPC-form field labels/descriptions built from a
  `params_schema` (these bypass `_section_from_dict`).
- `core/plugin/manifest.py:PluginManifest.from_dict` — plugin `description`,
  experimental/deprecation banners, and each RPC method's summary/description.
  `display_name` and `categories` stay **canonical** — they double as menu-path
  and dedup/identity keys ([/architecture/plugin-system.md](/architecture/plugin-system.md)),
  and are localized at the navigation-render seam instead (a tracked follow-up).
- `gui/tooltip.py:wrap_tooltip` and `gui/misc_helpers.py:TruncatingStatusBar` —
  the tooltip and status-bar funnels, which catch static imperative strings.
  Raw log output is deliberately not translated (dynamic, diagnostic).

# The kit

`build_tools/i18n/extract_strings.py` walks every `view.json` + `manifest.json`
(data, invisible to `pylupdate5`) **and** AST-scans `chisurf/**/*.py` for
`i18n.tr("…")` calls (the aliased token `pylupdate5` cannot see — `self.tr` is
deliberately skipped, as Qt would resolve it under a per-class context instead of
the flat `chisurf` one), then emits a generated stub of
`QCoreApplication.translate("chisurf", …)` calls covering all of them, then runs
`pylupdate5` over that stub plus all `.ui` forms to (re)generate/merge `chisurf/gui/i18n/chisurf_<code>.ts`
(existing human translations preserved). `lrelease` compiles `.ts` → runtime
`.qm`. Both are shipped as package data. Convenience wrappers:

- `pixi run i18n-extract` → regenerate `.ts` (after adding/changing UI text)
- `pixi run i18n-compile` → `lrelease` `.ts` → `.qm` (the `chisurf` task depends
  on it so a launched GUI always has fresh catalogues)

The order is **extract → translate/seed → compile**: run `i18n-extract` first so
the `.ts` carries every current source string, then fill translations, then
`i18n-compile`. `pylupdate5`'s merge is non-destructive — a re-extract preserves
already-finished translations and only adds/obsoletes sources — so a re-extract
after adding UI text keeps the existing catalogue. Canonical source terms are
governed by the [UI glossary](/references/ui-glossary.md); canonicalise labels
there **before** extracting so the catalogue has no near-duplicate keys.

Verified end-to-end by rendering the Lifetime model editor offscreen with
`gui.language: de`: the view.json panel titles show as *Faltung* / *Allgemein* /
*Korrekturen* / *Lebensdauern* / *Anisotropie*. The seeded German catalogue
covers ~400 finished terms: the main menu plus a broad sweep of shared UI chrome
(common buttons/actions, generic labels, panel titles — `Laden`/`Speichern`/
`Korrelation`/`Detektoren`/…). Deliberately **not** translated: units (`ns`,
`MHz`, `Å`), math symbols (`κ²`, `τ`, `g1`), format codes (`PTU`, `JSON`) and
dense per-plugin domain labels — those await domain review and fall through to the
English source (correct behaviour).

# Scope & status

Done: core seam, GUI bootstrap, data-driven + `.ui` localization, imperative
`i18n.tr(...)` extraction (AST scan), extractor + `en`/`de` catalogues (German
seed), glossary + micro-time label harmonisation. The preferred way to make a
plugin translatable is to port it to AutoForm — its strings move into `view.json`
and become translated + extracted for free (see `fcs_channel_preset` as the
reference: full AutoForm port + custom pairs section whose option strings and the
host's `i18n.tr` message boxes all render German).
Rich dock/plot tools that are **not** form-appropriate (a form port would drop
their dock area, live plots, or toolbar) instead get every static string wrapped
in `i18n.tr` in place — `tttr_time_windows` and `tttr_microtime_shifter` are the
references for that path (window + help titles, dock-tab labels, settings form,
toolbar actions, menu, plot labels, and static status-bar messages;
diagnostic/interpolated log lines stay English). Two anchoring gotchas, both
solved the same way — mirror the exact `i18n.tr(...)` expression everywhere a
piece of code re-derives a key from display text:

- **Toolbar object-name styling.** When a stylesheet targets buttons by an
  object name assigned from `action.text()`, the `name_map` keys must repeat the
  same `i18n.tr(...)` calls, or styling breaks under a non-English locale.
- **Persisted dock layouts.** `DockArea` keys tabs by the display name passed to
  `addTab`. A tool that hard-codes a default layout (its `widget_key`/`tab_name`/
  `tab_text` strings) must build those keys with the same `i18n.tr(...)` calls it
  passes to `addTab`, so the default layout still resolves under any locale (a
  saved layout from another locale falls back to that default — acceptable).
**Not translated at all: the ribbon.** `chisurf/gui/widgets/ribbon/` contains no
`i18n.tr` call and no `.ui` file, so its category/panel titles and its own chrome
are neither translatable nor extracted — switching language leaves the whole top
navigation in English. The main window's language-change handler rebuilds the
ribbon and its docstring claims that re-reads every string through the new
translator; that is true only of the ribbon buttons derived from **QActions**, so
the rebuild is not the fix. Details, the affected string list, and the vendored-
code caveat are in [/references/known-issues.md](/references/known-issues.md).

**Not translated at all: plugin names and menu categories.** A manifest's
`description` / `summary` / `experimental_message` / `deprecation_message` do go
through `tr()` in `chisurf/core/plugin/manifest.py`, but `display_name` and
`categories` are deliberately excluded at both the extraction and the load seam,
on the stated plan that they are "localized at the nav seam". No such seam
exists: the plugin-menu builder and the ribbon both split `display_name` on `:`
and render the parts verbatim, so every plugin entry stays English in every
locale — and the strings are absent from the catalogues, so no translator has
even been offered them. Note this is not fixable by wrapping the field:
`display_name` *is* the identity key (menu path, ribbon `plugin_order`,
`get_plugin_settings_path`), so translating it would move a plugin's settings
directory when the language changes. Identity and display have to be separated
first — see [/references/known-issues.md](/references/known-issues.md).

Deferred (tracked in [/specs/assessment.md](/specs/assessment.md)): wrapping the
remaining raw `setText`/`QMessageBox` call sites in `i18n.tr` (mostly the
not-yet-ported custom plugins), and converging the hand-built `.ui` terminology
to the glossary. (Localizing menu-path `display_name`/`categories` at the nav
seam was listed here as deferred polish; it is really a user-visible gap, so it
now lives in known issues with the identity-vs-display problem written out.)
