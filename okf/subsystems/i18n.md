# Production guards and finite family ownership

The literal guard uses the accepted measurement's 1,155 exact occurrence keys;
no scanner exclusions or new allowances were added. A new occurrence and a stale
allowance both fail. Repeated identical labels remain separate occurrences.
The existing literal scanner includes source line/column in its keys, unlike
some tooltip keys: moving a line requires checking the paired old/new occurrence,
not treating an unexplained new label as accepted debt.

The [ownership ledger](../../test/data/ui_debt_owners.json)
contains every remaining key exactly once. W6a owns spectroscopy/calibration
families, W6b burst, W6c microscopy, W6d modelling/trajectory/molecular viewers,
W6e calculators/decay, W6f core/model/experiment/legacy GUI surfaces, and W6g only
the shared native surface. The ownership test rejects missing, stale, duplicate,
unscoped or noncallable-check assignments. Family closure requires actual runtime
translation or reachable meaningful help, preserved controls/data, removal from
both allowance and ledger, and the named production guard. Coordinate disjoint
family batches; no single shared owner inherits all plugin repairs.

# Purpose

ChiSurf's user-facing text lives on two surfaces: the data-driven
`*.view.json` (AutoForm), guide and `manifest.json` plugin specs, and imperative
GUI calls (window titles, message boxes, custom-section labels). There are no
Qt Designer `.ui` forms. This subsystem makes the **data-driven** surface
translatable from a single seam, plus imperative strings that are explicitly
wrapped in `core.i18n.tr(...)`, and ships the kit that extracts, compiles, and
loads catalogues. English is the canonical source language.

# Design

**Shared toolkit seam.** Translation lives in `emtk.i18n` (emtk repo), shared
by ChiSurf, chimol and ndX: `tr(source, context=None, *, domain=None)` looks a
string up `domain -> "emtk" -> source`; `add_catalogue(domain, dir)` registers
per-language Qt Linguist `.ts` (parsed without Qt) or JSON catalogues, lazily
and once per (domain, language); `set_language`/`language`/`generation`;
`mark()` for deferred strings; `use_domain()` while a panel draws an app's
spec. ChiSurf's `core.support.i18n.tr` delegates to it with domain
`"chisurf"` whenever no Qt backend is bound, registering `chisurf/gui/i18n`
and `gui.language` (via `set_language_provider`) on first use, so the default
English setting stays the identity. `chisurf.emtk.i18n.install` is that
registration plus picking the language. A spec form translates labels once,
where it measures them -- measuring the source and drawing the translation
clipped every German button.

**Qt-free core seam.** `chisurf/core/i18n.py` exposes `tr(text, context="chisurf")`
that defaults to the **identity** function and holds a swappable backend. The
core/server path stays import-clean of any GUI toolkit (the same rule that keeps
[/subsystems/core.md](/subsystems/core.md) and `core/dataspec` Qt-free); the GUI
binds a real backend at startup. `get_locale()`/`set_locale()` read/write the
`gui.language` setting (two-letter code; default `en`).

**GUI bootstrap.** `chisurf/emtk/i18n.py` registers the
`chisurf/gui/i18n/chisurf_<code>.ts` catalogues with `emtk.i18n` under the
`chisurf` domain; the toolkit parses them lazily, nothing is compiled, and no
Qt translator is installed.

**Persistence.** A picked language is written to `gui.language` in the user's
`settings_chisurf.yaml` by `core/settings/settings_utils.py:set_language`, which
is what makes the choice survive a restart — the translator is installed from
that value at startup. The writer used to take `data.get('gui', {})`, whose
default is an **orphan** dict never attached to `data`, so on a settings file
with no `gui:` section the language was written into nothing and silently
reverted on the next start (the same bug was in `set_use_ribbon` and
`set_acquisition_settings`); all three now assign the section back before
dumping. Guarded by `test/settings/test_settings_utils.py`.

**Language pickers.** `gui/widgets/language_selector.py` hosts the two reusable
pickers — a labelled combo (`LanguageSelector`, used in Settings) and a compact
toolbar flag-dropdown (`LanguageFlagSwitcher`, used in the ribbon corner). Both
discover locales from the shipped `.qm` catalogues, persist + live-apply through a
shared helper, and re-sync via the app-wide `language_notifier`. Flags are
**painted `QIcon`s** built by `gui/i18n.py:language_flag_icon` (a small QPainter
recipe per locale — striped tricolours, a Union Jack for `en`, disc/star for
`ja`/`zh`, a two-letter pill fallback), **not** regional-indicator emoji: emoji
flags render unreliably in Qt menus/buttons (many font stacks show the two letters
in dotted boxes), so the emoji `language_flag` is kept only for tooltips. The icons
are cached by `(code, height)`.

**Live switching.** A language switch takes effect on the next emtk frame:
every view spec and `i18n.tr` call reads its text through the seam on each
build, so an open window follows without a re-translation shim (the Qt-era
`retranslate_from_ui`, which re-parsed `.ui` XML, is gone with the forms;
[INC-13](/specs/assessment.md#inc-13) is closed).

**Central localization seams** (all route through `core.i18n.tr`):

- `core/dataspec/__init__.py:_section_from_dict` — every text-bearing field of a
  `view.json` section (title, label, description, suffix, placeholder, add/remove
  labels, axis labels, nested item/button/column text). One choke point → all
  view specs.
- `core/dataspec/rpc.py` — RPC-form field labels/descriptions built from a
  `params_schema` (these bypass `_section_from_dict`).
- `core/plugin/manifest.py:PluginManifest.from_dict` — plugin `description`,
  experimental/deprecation banners, and each RPC method's summary/description.
  `display_name` and `categories` stay **canonical** — they double as menu-path
  and dedup/identity keys ([/architecture/plugin-system.md](/architecture/plugin-system.md)),
  and are localized at the navigation-render seam instead (a tracked follow-up).
- `gui/tooltip.py:wrap_tooltip` and `gui/misc_helpers.py:TruncatingStatusBar` —
  the tooltip and status-bar funnels, which catch static imperative strings.
  Raw log output is deliberately not translated (dynamic, diagnostic).

# The kit

`build_tools/i18n/extract_strings.py` walks every `view.json`, guide and
`manifest.json` **and** AST-scans `chisurf/**/*.py` for `i18n.tr("…")` calls
(`self.tr` is deliberately skipped — it would resolve under a per-class context
instead of the flat `chisurf` one), then merges them in pure Python
(`merge_catalogue`) into `chisurf/gui/i18n/chisurf_<code>.ts`, preserving
existing human translations. The `.ts` files are shipped as package data and
read directly. Convenience wrappers:

- `pixi run i18n-extract` → regenerate `.ts` (after adding/changing UI text)

The order is **extract → translate/seed**: run `i18n-extract` first so the `.ts`
carries every current source string, then fill translations; there is no compile
step. The merge is non-destructive — a re-extract preserves
already-finished translations and only adds/obsoletes sources — so a re-extract
after adding UI text keeps the existing catalogue. Canonical source terms are
governed by the [UI glossary](/references/ui-glossary.md); canonicalise labels
there **before** extracting so the catalogue has no near-duplicate keys.

Russian (`ru`) ships as the third translated locale and is currently the
**most complete** catalogue: 3100 finished terms against 2938 (`de`) and 2878
(`fr`). It was seeded by extracting `chisurf_ru.ts` (`--locales ru`, so the
shared `de`/`fr` catalogues other instances may be editing are not rewritten),
translating every source string the German catalogue covers, and then the ~290
wordy strings German does not (newer plugins: burst fusion, flow maps, the PSF
calculator). The 356 sources still untranslated are units, math symbols, format
codes, Qt signal/objectName artifacts and keyboard shortcuts — those must stay
English. Verified offscreen with `gui.language: ru`: `tttr_time_windows` renders
fully Russian (*Обработать* / *Настройки* / *Файлы* / *Предпросмотр* / *Сводка* /
*Готово*), the FCS calculator's view.json panels read *Ограничение* / *Диффузия /
объём* / *Заполненность*, and both pickers list **Русский** with a painted
tricolour. Two gaps the screenshots exposed are *not* Russian-specific and are
tracked with the deferred work below: raw `QRadioButton`/`QAction` text in
`fcs_calculator/wizard.py` and `img_flow`'s toolbar is neither wrapped in
`i18n.tr` nor extracted, so it stays English in every locale.

**Spanish (`es`) and Portuguese (`pt`)** were seeded the same way and to the same
scope — 3088 finished terms each, extracted with `--locales es pt` and filled
from one *paired* batch file per chunk (`{index: [es, pt]}`), so the two
Romance locales are translated against the same reading of each source string
rather than twice from scratch. Portuguese follows **European** usage
(*ficheiro*, *definições*, *ecrã*-style vocabulary, `detetor`/`deteção` with the
post-1990 orthography), which is a decision worth knowing before anyone
"corrects" it towards pt-BR. The residual 394 untranslated sources per locale
are the same class as Russian's — units, symbols, format codes, signal names.
Shipping a new locale therefore needs **no code**: `available_languages()`
discovers it from the `.qm`, and the endonym + painted flag are already in
`gui/i18n.py` for every locale in that table.

Verified end-to-end by rendering the Lifetime model editor offscreen with
`gui.language: de`: the view.json panel titles show as *Faltung* / *Allgemein* /
*Korrekturen* / *Lebensdauern* / *Anisotropie*. The seeded German catalogue
covers ~400 finished terms: the main menu plus a broad sweep of shared UI chrome
(common buttons/actions, generic labels, panel titles — `Laden`/`Speichern`/
`Korrelation`/`Detektoren`/…). Deliberately **not** translated: units (`ns`,
`MHz`, `Å`), math symbols (`κ²`, `τ`, `g1`), format codes (`PTU`, `JSON`) and
dense per-plugin domain labels — those await domain review and fall through to the
English source (correct behaviour).

# Scope & status

Done: core seam, GUI bootstrap, data-driven localization, imperative
`i18n.tr(...)` extraction (AST scan), extractor + `en`/`de`/`es`/`fr`/`pt`/`ru`
catalogues,
settings persistence of the picked language, glossary + micro-time label
harmonisation. The preferred way to make a
plugin translatable is to port it to AutoForm — its strings move into `view.json`
and become translated + extracted for free (see `fcs_channel_preset` as the
reference: full AutoForm port + custom pairs section whose option strings and the
host's `i18n.tr` message boxes all render German).
Rich dock/plot tools that are **not** form-appropriate (a form port would drop
their dock area, live plots, or toolbar) instead get every static string wrapped
in `i18n.tr` in place — `tttr_time_windows` and `tttr_microtime_shifter` are the
references for that path (window + help titles, dock-tab labels, settings form,
toolbar actions, menu, plot labels, and static status-bar messages;
diagnostic/interpolated log lines stay English). Two anchoring gotchas, both
solved the same way — mirror the exact `i18n.tr(...)` expression everywhere a
piece of code re-derives a key from display text:

- **Toolbar object-name styling.** When a stylesheet targets buttons by an
  object name assigned from `action.text()`, the `name_map` keys must repeat the
  same `i18n.tr(...)` calls, or styling breaks under a non-English locale.
- **Persisted dock layouts.** `DockArea` keys tabs by the display name passed to
  `addTab`. A tool that hard-codes a default layout (its `widget_key`/`tab_name`/
  `tab_text` strings) must build those keys with the same `i18n.tr(...)` calls it
  passes to `addTab`, so the default layout still resolves under any locale (a
  saved layout from another locale falls back to that default — acceptable).
**Not translated at all: the ribbon.** `chisurf/gui/widgets/ribbon/` contains no
`i18n.tr` call, so its category/panel titles and its own chrome
are neither translatable nor extracted — switching language leaves the whole top
navigation in English. The main window's language-change handler rebuilds the
ribbon and its docstring claims that re-reads every string through the new
translator; that is true only of the ribbon buttons derived from **QActions**, so
the rebuild is not the fix. Details, the affected string list, and the vendored-
code caveat are in [/references/known-issues.md](/references/known-issues.md).

**Not translated at all: plugin names and menu categories.** A manifest's
`description` / `summary` / `experimental_message` / `deprecation_message` do go
through `tr()` in `chisurf/core/plugin/manifest.py`, but `display_name` and
`categories` are deliberately excluded at both the extraction and the load seam,
on the stated plan that they are "localized at the nav seam". No such seam
exists: the plugin-menu builder and the ribbon both split `display_name` on `:`
and render the parts verbatim, so every plugin entry stays English in every
locale — and the strings are absent from the catalogues, so no translator has
even been offered them. Note this is not fixable by wrapping the field:
`display_name` *is* the identity key (menu path, ribbon `plugin_order`,
`get_plugin_settings_path`), so translating it would move a plugin's settings
directory when the language changes. Identity and display have to be separated
first — see [/references/known-issues.md](/references/known-issues.md).

Deferred (tracked in [/specs/assessment.md](/specs/assessment.md)): wrapping the
remaining raw `setText`/`QMessageBox` call sites in `i18n.tr` (mostly the
not-yet-ported custom plugins — `fcs_calculator/gui/wizard.py`'s constraint radio
buttons and `img_flow`'s toolbar `QAction`s are the two the Russian screenshots
caught, and they stay English in *every* locale because they are not extracted at
all). (Localizing menu-path `display_name`/`categories` at the nav
seam was listed here as deferred polish; it is really a user-visible gap, so it
now lives in known issues with the identity-vs-display problem written out.)
