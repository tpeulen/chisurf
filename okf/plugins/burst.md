The `burst/` group covers the confocal single-molecule FRET (smFRET) burst workflow: bursts are selected from Time-Tagged Time-Resolved (TTTR) photon streams, background is estimated, and each burst yields FRET, variance, lifetime and correlation observables that a browser inspects. This pipeline is the subject of [PRD-04](/prds/prd-04.md) (burst pipeline).

| Plugin dir | Display name | What it does |
|---|---|---|
| `burst_analysis` | Burst Analysis | Integrated burst workflow bundling selection, BVA, MLE, browser and background estimation in one navigation-shell window. Also ships a Qt-free `api/workflow.py` facade (`BurstWorkflow`) for non-programmers. |
| `burst_selection` | Burst Selection | Selects photon bursts from TTTR data and computes per-burst FRET indicators. |
| `burst_background` | Burst Background Estimation | Estimates detector background rates from TTTR burst data. |
| `burst_analysis` (IRF/bg step) | — | Extracts a per-detector IRF **and** background rate from the **non-burst** photons of a measurement, via `BurstWorkflow.estimate_irf_background` / `Bursts.irf_background` (core: `chisurf/core/fluorescence/burst/irf_bg.py`). |
| `burst_bva` | BVA | Burst Variance Analysis — tests whether FRET-efficiency spread exceeds shot-noise (dynamics detection). |
| `burst_2cde` | 2CDE | FRET-2CDE / ALEX-2CDE per-burst dynamics feature (Tomov et al. 2012) — kernel-density estimate of two photon streams flags within-burst kinetics and acceptor blinking. |
| `burst_h2mm` | H2MM | Photon-by-photon Hidden Markov Model — resolves sub-burst FRET-state dynamics on the microsecond scale via a self-contained numba engine, with BIC/ICL state selection and Viterbi dwell/transition analysis. |
| `burst_ebfret` | ebFRET (binned traces) | Empirical-Bayes Gaussian HMM for **binned** FRET-efficiency time traces (TIRF/camera-style, intensity-vs-time) — the complement to the photon-by-photon `burst_h2mm`. Ports ebFRET's per-trace VBEM + shared-prior hyperparameter loop; scans state counts, recovers per-state emission means/precisions, and does Viterbi dwell/transition analysis. |
| `burst_mle_analysis` | Burst MLE | Maximum-likelihood (2I*) fluorescence-lifetime analysis of single-molecule bursts, via the shared tttrlib `fit2x` harness (`chisurf/core/fluorescence/mle/`). |
| `burst_fcs_correlator` | Burst-wise FCS | Computes correlation functions per burst from Burst-ID (`.bst`)/BUR files. |
| `burst_browser` | Burst Browser | Inspects burstwise analysis tables and plots. |
| `bid_to_analysis` | BID→Analysis | Converts Seidel-style BID (Burst ID) files into a burstwise analysis folder (BUR/Info/MTI, optional HDF5/SL5) that ChiSurf and companion tools consume. |

`burst_mle_analysis` fits a single fluorescence lifetime + anisotropy per burst per detector by Poisson maximum likelihood. The estimator itself is tttrlib's C++ `Fit23` (the Maus-2001 `2I*` MLE); ChiSurf wraps it through one Qt-free seam, `chisurf/core/fluorescence/mle/` (`Fit2x`, `Fit2xSettings`, `Fit2xResult`, `assemble_vv_vh`), rather than reconstructing the raw `tttrlib.Fit23` in every consumer. The batch worker (`_mp_worker.py`), the wizard's batch pass, and the image-MLE plugins (`microscopy/img_pixel_mle`, `microscopy/sm_image_mle`) all fit through this harness. See the [fitting subsystem](/subsystems/fitting.md) for the harness and the complementary in-core `noise_model="poisson"` (`2I*`) objective now available to the ordinary TCSPC decay fits.

The `MLELifetimeAnalysisWizard` is a QMainWindow, but the `burst_analysis` shell embeds it by `takeCentralWidget()`-ing the wizard and hosting only that central widget — an embedded QMainWindow swallows clicks on native macOS, so the shell embeds the plain content and keeps the wizard object as the workflow's `"mle"` logic panel (it owns all fit state and widget references; `central._mle_wizard` back-refers to it). **Lifetime invariant:** the wizard is re-parented onto that extracted central widget as a plain hidden child (`_burst_mle` does `wizard.setParent(central, Qt.Widget)` + `hide()`), so wizard and content share one branch and one lifetime. This is load-bearing: the wizard's fit buttons live under `central` and are wired to `wizard` slots, so if the wizard were left in a separate branch (e.g. parented to the workflow window) a window/child cleanup could destroy it while the buttons survived — a later click would then fire a slot on a deleted C++ object (`wrapped C/C++ object … has been deleted`). It must be reparented as `Qt.Widget`, not `Qt.Window`: a `Qt.Window` reparent stays a top-level window that macOS actually shows — an empty little traffic-light window floating over the panel, whose close deletes the wizard and re-triggers the crash. A hidden non-window child never renders (so no QMainWindow-as-child click-swallow) and is not a closeable window. Pinned by `test_mle_wizard_shares_lifetime_with_embedded_widget`.

**Action toolbar.** The eight fit-page actions (Run, ⚡ Auto-optimize, ✨ Auto IRF/BG, the IRF-model combo, 📁 IRF & Background…, 🎯 Optimize + iteration count, 💾 Save) live in one action bar across the **top of the whole Burst-MLE page** — above the controls|plots splitter (`_build_parameters_tab` stacks `[toolbar, splitter]` in a QVBoxLayout), so it spans the full panel width. It is a plain `QFrame` embedded as a widget, not `addToolBar()` (a QMainWindow toolbar would not render in the embedded workflow, which hosts only the central widget), and uses the shared `FlowLayout` so the buttons wrap to another row when the panel is narrow instead of hiding overflow behind a `»` menu. It must sit above the splitter, not inside the narrow left controls column, or the embedded dock clips the wrapped rows and covers the buttons. Pinned by `test_action_buttons_live_in_the_top_toolbar`.

**Polarisation corrections (G factor / l1 / l2).** These per-detector calibration constants live on the detector definition (`channel_definer.detectors[det]`, edited in the setup/Channels step) and feed the fit's anisotropy. The fit page shows them **read-only** for the current detector (the "Shift · scatter · G/l1/l2" section, refreshed on each detector switch), since the Detector Definition tab is hidden in the embedded workflow. They are deliberately not part of the wizard's transient per-detector UI-state cache: `_ensure_channel_state(det)` seeds them from that detector's own definition (not the *current* detector) and `_apply_ui_state` does not write them back — the definition is the single source read live via the getters. Restoring them through the setters (which poke the definition's table cells by row/column) previously mis-targeted the cells and **swapped one detector's l1/l2 onto another** on repeated switches, so the fit silently used the wrong corrections. Pinned by `test_fit_page_displays_per_detector_g_factor_l1_l2`.

`burst_h2mm` follows the client-server standard: a Qt-free numba engine (`core/h2mm.py` — cached `A^Δt` and transition-count `ρ` tensors, scaled forward-backward, Baum-Welch EM, Viterbi+ICL) under a database-free RPC service (`burst_h2mm.jobs.compute`) with a thin `H2mmClient` GUI, and it embeds as step 6 of the `burst_analysis` shell, inheriting the burst folder and channel definitions from the shared workflow context. The engine, criterion, scan `patience`, and (optional) trained surrogate are selectable from the GUI settings tab, the `h2mm compute` CLI (`--engine`/`--surrogate`/`--patience`/`--refine-iters`), and the API. The GUI runs the fit **off the UI thread** (a `QThreadPool` `Worker`) behind an `EnhancedProgressDialog` with a computed **ETA** and a Cancel button, and the model-selection + FRET plots **update live** after each state-count fit (a `progress(done, total, fits)` callback threaded through `analyze`/`scan_states`/`run_analysis`); the GUI defaults to the fastest method (`em-float32`) with early-stop (`patience=1`) on. To make the engine's `parallel=True` kernels actually use the CPU, the shipped thread settings now default `numba_num_threads: "auto"` (resolved to CPU-cores − 1 in `env_bootstrap`, with MKL/OMP kept at 1 to avoid oversubscription) — previously pinned to `"1"`, which ran the whole engine single-threaded in-app. Each run writes a defined output set to `<folder>/h2mm/`: `h2mm_result.json` (model + scan), a **per-photon** `h2mm_photons.h5` (Viterbi `State`, macro/micro time, channel, stream) and a **per-burst** `h2mm_bursts.csv` — plain numeric tables (time column `Mean Macro Time (s)`) that open directly in **ndxplorer** via its CSV/MFD-HDF5 readers (`core/export.py`, `core/photons.py::PhotonMeta`). The per-burst table carries the MFD column names ndX keys its **FRET-line** plot on — `Mean Microtime (green)` (its FRET-line X axis: the per-burst mean donor micro time in ns, an IRF-uncorrected lifetime proxy, computed from the run's `MeasDesc_Resolution`), `Proximity ratio` (its default Y axis) and a measured `FRET efficiency` — built from the donor/acceptor role stream groups (divisor-aware) alongside the H2MM `Dominant State` / `Number of Transitions` for colouring, so an ndX-loaded run lands on the E-vs-donor-lifetime FRET line with no remapping. A **per-dwell** `h2mm_dwells.csv` (`build_dwell_table`) is also written — one row per Viterbi dwell (`State`, `Number of Photons`, `Dwell Time (ms)`, measured E/S, `Mean Microtime (<name>)`, and an `Is Edge` flag for burst-boundary dwells) — because **dwell filtering** (min photons, drop burst-edge dwells, select by state/duration) is done downstream in ndX, which filters rows, so the dwell must be a first-class exported unit. Theory + usage live in [`docs/H2MM.md`](../../docs/H2MM.md); the plugin ships its examples **inside the package** at `burst_h2mm/examples/` — `H2MM_01_Simulated_smFRET.ipynb` (end-to-end: simulate smFRET with `tttrlib` → fit → compare engines → export ndX tables) and `generate_example_data.py` (writes a real, loadable Photon-HDF5 + `.bur` example dataset, runnable via `python -m …burst_h2mm.examples.generate_example_data`).

The **Results panel** is a burstH2MM-style dashboard (`gui/tool.py`, pyqtgraph). Each of its seven plots is an **independent dock** in the tool's dock area (not a single fixed `GraphicsLayoutWidget` grid), so every plot can be resized, tabbed, maximised or dragged into any split arrangement; the docks arrive in a default two-column layout (`_build_plot_docks` + `_apply_default_plot_layout` via `DockArea.set_layout_state`) that mirrors the familiar dashboard, and the user's rearrangement persists via `_save_dock_layout`/`_restore_dock_layout` (BVA-style, applied **synchronously in `__init__`** — never on `showEvent`, which fought the embedded navigation lifecycle and could leave a deleted plot widget registered, crashing a later show; `DockArea.showTab` / its context menu additionally prune any C/C++-deleted page via `_is_deleted`). The plots are: a dwell **E histogram** — or a dwell **E–S scatter** when an acceptor-excitation stream is defined — the **transition-density plot** (E before vs E after), **BIC/ICL model selection**, per-state **dwell-time distributions**, per-state **fluorescence-decay** (nanotime, micro-time by Viterbi state), a **transition-rate matrix** heatmap (`ana.trans_rates`, 1/s, per-cell value labels), and an interactive per-burst **Viterbi state-path** viewer (◀/▶ + spinbox, "dynamic bursts only" filter; photons coloured by state, marker shape by stream). The dwell FRET panel also carries **transition-rate arrows** between state nodes (burstH2MM `trans_arrow_ES`; width ∝ rate — on the E–S nodes, or a kinetic scheme above the E histogram in 2-colour mode). It is fed by `core/analysis.py`, which decodes the Viterbi path once (`H2mmAnalysis.path`) and returns a `dwells: list[Dwell]` carrying each dwell's *measured* E/S (from photon counts, not the model emission matrix). An **optional third "Acceptor (Aex)" stream** (channels-tab combo, defaulting to the PIE "yellow" detector) turns on µsALEX/PIE **stoichiometry** `S = (D+A)/(D+A+A_ex)` via `state_stoichiometry()` (per-state, and per-dwell measured); with only two streams the analysis degrades cleanly to FRET-E only (`S = NaN`, `H2mmResult.has_alex=False`). Every panel except the nanotime decay renders without per-photon metadata, so results loaded without `bundle.meta` still plot. The same figures are reproduced on tttrlib's own C++ H2MM engine in the tttrlib tutorial `examples/single_molecule/plot_h2mm_analysis.py` (`simulate_bursts` → BIC state-count scan → `viterbi_path` → dwell/transition extraction).

Further burstH2MM capabilities are ported. (a) **Bootstrap uncertainty** — an on-demand "± Uncertainty" toolbar action (`bootstrap_uncertainty`, background Worker) resamples bursts with replacement (`_subset_bursts` rebuilds a `BurstPhotons` from the CSR arrays), refits, label-aligns replicates by sorting states on E, and overlays per-state E/S percentile error bars on the E–S scatter. (a′) **Profile-likelihood uncertainty** — a "📈 LL scan" action (`profile_likelihood`) sweeps each state's E (and S) with the other parameters fixed and recomputes the fixed-model forward log-likelihood (`fixed_loglik` = one EM map, no update), reading the CI where the deviance `2·(logLmax−logL)` crosses χ²₁ (3.84 → 95 %); a `LikelihoodScanDialog` plots the deviance-vs-parameter curves with MLE/threshold markers and the bootstrap CI overlaid — the two disagree on *unidentifiable* (flat-profile) states, which is the useful signal. (b) **Nanotime divisors** (`H2mmSettings.divisors`, "Nanotime divisors" spinbox) — `bursts_from_dataframe(..., divisors=N)` splits each base stream into N micro-time quantile bins (contiguous per-base blocks, `stream_index // N` = role) so the HMM uses fluorescence lifetime and can separate states that share an apparent E but differ in τ. To support divisors the FRET/stoichiometry/measured-E-S helpers are **role-group aware** (a role is a set of stream indices), and `analyze(..., divisors)` derives and stores the donor/acceptor/Aex stream blocks on `H2mmAnalysis`. (c) **ndxplorer FRET-line export** — rather than an in-plugin E–τ plot (redundant with ndX's own static/dynamic FRET-line plot), the per-burst export (`core/export.py::build_tables`) carries the MFD column names ndX auto-selects — `Mean Microtime (green)` (mean donor micro time in ns, an IRF-uncorrected donor-lifetime proxy, the FRET-line X axis) and `FRET efficiency` / `Proximity ratio` (measured apparent E, the default Y axis) — so H2MM results open straight onto that plot, mirroring how BVA augments the MFD burst table. Headless coverage in `tests/test_services.py`, `tests/test_export.py` (FRET-line columns + `write_result_tables` round-trip) and `tests/test_gui.py` (error-bar overlays).

The numba engine is tuned to run faster than the reference `H2MM_C` while staying numerically equivalent. Four independent optimisations compound (each guarded by the A/B-vs-`H2MM_C` tests):

- **Deferred ρ contraction.** The parallel E-step never forms the ξ tensor per gap (`O(N·n⁴)`); it accumulates a per-unique-Δt weight `W[slot,k,m]` in `O(N·n²)` and contracts `ξ = Σ W·ρ` once per slot in the serial reduction, so `rho_cache` is read `n_slots` times instead of N.
- **Two-pass E-step.** Occupancy (γ) and transition (W) statistics are folded into a single backward sweep, and β is held as two `(n,)` vectors so the full `(N, n)` backward array is never materialised — halving the large-array memory traffic.
- **Cache locality (the real memory win).** The engine is memory-bandwidth-bound, so `α`/`scale` are kept in small **per-thread scratch buffers** (sized to the longest burst, reused across bursts, hot in L1/L2) rather than a shared `(N, n)` array — removing the largest DRAM stream. A controlled A/B at 2.4M photons (one EM map, isolated) shows **1.25–1.6× on the E-step** (biggest at `n=3`), flat per-photon cost across dataset size (no large-`N` cliff), and tens of MB lower peak memory.
- **Narrow integers (footprint, ~neutral speed).** The per-photon index reads (`streams`→`int8`, `gap_slot`→`int16`, from `int32`) shrink the index-array footprint ~3×. Once `α` is out of DRAM these are a small share of traffic, so the isolated speed effect is within noise (0.94–1.11×); kept for the memory-footprint reduction on very large datasets, not for throughput.
- **SQUAREM acceleration** (default) reaches the identical EM fixed point in far fewer maps via squared extrapolation with a monotonicity safeguard (≈2.5× fewer maps at 2 states, ≈6× at 3 states on well-separated data).
- **Spectral cache build.** For sparse photon streams (long inter-photon Δt, `n ≥ 3`) `A^Δt`/`ρ` are built from an eigendecomposition (divided differences) instead of binary exponentiation, with a conditioning-guarded fall-back to pair-power; dense high-count-rate data keeps pair-power.

These back-ends are unified behind a single compute-engine selector (`core/engines.py`: `em` / `em-float32` / `surrogate` / `surrogate-refine`), so `analyze`/`scan_states`, the CLI, and the GUI all choose the fitting back-end by name (model selection always scores fitted models by BIC/ICL; only *how* each is fitted changes; surrogate engines fall back to exact EM where no trained model is supplied).

At the **model-selection** level, an opt-in `patience` early-stops the state-count scan: the BIC/ICL curve is U-shaped and the over-fit high-`k` fits are the most expensive (a redundant state makes a flat likelihood ridge, so they run to `max_iter` without converging), so stopping once the criterion has clearly turned upward gives a safe ~1.6× faster scan with the same selection (`patience=None` fits every count unchanged). Skipping the per-`k` Viterbi for BIC selection was measured to be negligible (<1 % of a fit) and not adopted.

An opt-in `single_precision` mode (the `em-float32` engine) runs the hot loop and caches in `float32` to roughly halve their bandwidth (≈1.9× at 3 states); it is explicitly **approximate** (does not meet the reference tolerance) for exploratory fits on very large datasets. The engine also re-pins `NUMBA_NUM_THREADS` to numba's launched pool size before compiling, so ChiSurf's startup thread-env rewrite cannot break a late (e.g. `float32`) kernel compile.

**Viterbi** decoding is likewise parallelised over bursts (`_viterbi_all`, a `prange` mirror of the E-step), ≈3× faster than the former serial loop and called on every model-selection scan (for ICL) and final path. State-splitting warm-starts for the multi-state model-selection scan were evaluated and **rejected**: a single split cannot undo the state merging in the smaller fit, so it reached worse optima than random restarts on well-separated data — a robust version would need full split+merge SMEM.

An **optional** amortised neural estimator (`core/surrogate.py`, see [PRD-60](/prds/prd-60.md)) offers a further fast path for large datasets: a small scikit-learn MLP trained once on simulator draws predicts `(prior, trans, obs)` in one forward pass (simulation-based inference), used via `fit_states(..., surrogate=…, refine_iters=…)`. It is a *replacement* for EM, not an initialiser — measurements showed seeding EM even from the exact generative parameters barely cuts its iteration count, because EM's cost is the finite-sample last mile to the dataset-specific MLE. The estimate is approximate (appropriate for over-determined data; use EM for final numbers and model selection); it ships disabled with no pretrained model and falls back to EM when scikit-learn is absent. The estimator now also has a **C++ implementation in the photon-processing library** (a reusable `NeuralNet` class plus an `H2mmSurrogate` adapter), so a surrogate trained here with scikit-learn can be exported via `SurrogateModel.export_json()` to a language-neutral JSON schema and executed by the C++ engine — `core/surrogate_tttrlib.py` is the adapter and `core/engines.py` routes JSON surrogates to it, keeping pickled models on the scikit-learn path. The two agree numerically: the C++ feature extractor reproduces the numba kernel to 1e-12 (which required matching NumPy's histogram bin-edge handling exactly and disabling FMA contraction in the sliding-window sum). Measured, the surrogate is ~10x faster per estimate than EM and trains end-to-end in seconds; on accuracy the two split by state separation rather than one dominating — the surrogate is ~4x better where the states are barely separated and the MLE is unidentifiable, EM better on well-separated states — so an averaged comparison should not be quoted.

`burst_ebfret` covers the one class of smFRET data the burst group otherwise lacked: **binned intensity-vs-time FRET traces** from wide-field/TIRF cameras, rather than confocal photon streams. It is a Qt-free headless port of ebFRET (van de Meent et al.; itself a re-implementation of vbFRET) with two nested loops — a per-trace variational-Bayes EM over a univariate Gaussian-emission HMM (Dirichlet priors on initial/transition distributions, a Normal-Gamma prior on each state's mean/precision, linear-scaled forward-backward) and an outer empirical-Bayes loop that re-estimates the shared prior from all trace posteriors via conjugate h-step updates (Dirichlet Newton + Normal-Gamma moment-matching, ported from ebFRET's `+dist/*/h_step.m`). `core/analysis.py` scans state counts, selects the highest-evidence model, and returns per-state emission summaries, a Viterbi transition-count matrix, and dwell segments; exposed via a `burst_ebfret.jobs.compute` RPC service and an `ebfret compute` CLI over the ebFRET "stacked" `.dat` format. It is validated for state recovery against ebFRET's own `simulated-K04-N350` dataset (vendored under the plugin's `tests/data/`): at K=4 it recovers the two well-separated interior states within 0.05 of ebFRET's fitted `[0.33, 0.516]`, the endpoints differing only because this port fits the uncorrected proximity ratio `A/(D+A)` while ebFRET fits a background-subtracted signal. Porting this one algorithm closes the functional gap behind a whole family of TIRF tools on fret.community (ebFRET, vbFRET, HaMMy, SMACKS). Scope is currently the single-prior D=1 path; the prior-mixture (subpopulation) layer, SMD/session I/O, and a GUI tool are follow-ups. It is marked `experimental` and `menu_hidden`.

`burst_analysis` additionally exposes a headless, non-programmer facade at `burst_analysis/api/workflow.py`: `BurstWorkflow` bundles MMFDB dataset registration → burst selection → BVA → H2MM behind one plain-English line per step (`.demo()`/`.connect()`, `register`/`register_all`, `select_bursts`, then `Bursts.bva()` / `Bursts.h2mm()`, each result carrying `.plot()`/`.summary()`). Generality comes from a declarable `Setup` of named `Detector`s (routing channels + optional micro-time windows), built with `Setup.from_channels(green=(0,8), red=(1,9), yellow=(2,10), …)` for any number of dyes and mirroring ChiSurf's `{name: {chs, micro_time_ranges}}` detector model. FRET is **not** stored in the setup — no donor/acceptor or "two-colour" naming is baked in; the FRET pair is chosen per analysis (`bva("green","red")`, `h2mm(donor=…, acceptor=…)`), defaulting to the first two detectors, while H2MM always models every detector as a stream (true N-colour). Optional/inferred TTTR `file_type`, multi-dataset selection, and a selectable burst-search `method` (`burst`/`count_rate`/`cusum`/`bocpd`/`kalman`) round it out, with every parameter defaulted so the simple case stays one line. Detector micro-time windows feed BVA/H2MM stream assignment (not the selection filter, which *rejects* micro-time ranges); the default `method="burst"` is the sliding-window search that honours `min_photons`. `BurstWorkflow.simulate(fret=…, exchange_rate=…)` generates a **known-ground-truth** dataset with tttrlib 0.27's confocal simulator (`SimEngine.from_dict` → `to_tttr` → real SPC), registers it in MMFDB, and returns a `Simulation(handle, setup, truth)` so recovered states can be validated against the defined FRET/exchange. The `H2mm` result exposes the model-selection `scan` and canonical H2MM plots — `plot_states`, `plot_model_selection` (BIC/ICL vs states), `plot_transitions` (rate matrix), `plot_dwell_times`, and a 2×2 `plot()` dashboard — plus selectable analysis modes (`engine` em/em-float32/surrogate, `criterion` bic/icl) and per-analysis FRET-pair choice. Worked examples: `modules/mmfdb/examples/mmfdb_00_overview.ipynb` (real data, full pipeline) and `chisurf/plugins/burst/burst_h2mm/examples/H2MM_02_MMFDB_GroundTruth.ipynb` (simulated ground truth → MMFDB → H2MM recovery + analysis modes); headless coverage: `test/plugins/burst/test_mmfdb_burst_workflow.py` and `test/plugins/burst/test_mmfdb_h2mm_simulation.py`.

**Photon-filter pipeline and the delta-macro-time pre-filter.** `burst_selection/api/selection.py::apply_photon_filters` turns a TTTR object into the per-photon selection mask that `find_bursts` groups into bursts; both the live GUI preview (`gui/client.py`) and the backend RPC service (`backend/services.py`) go through it. It composes three photon-stream pre-filters (channels, micro-time ranges, and the delta-macro-time interval) with the configured burst search (`count_rate`/`burst`/`cusum`/`kalman`/registry-driven `tttrlib` — the retired `bocpd` mode raises). The **delta-macro-time interval** (`DeltaMacroTimeFilterSettings`, min/max inter-photon gap in ms) is a genuine pre-filter on the photon stream the search *sees*, not a mask AND-ed onto the search result — AND-ing it afterwards was a no-op, because burst photons already have a small inter-photon gap so the interval never removed any of them. `_search_on_delta_filtered_stream` builds the reduced stream with tttrlib (`get_tttr_by_selection`, indices as `int32`), runs `_run_burst_search` on it, and maps the detected photons back to the original index space. Semantics are **exclude-from-search-only**: a photon outside the interval can no longer seed or extend a burst, but a burst that spans it still counts it (bursts are found over the original photons, so the mask stays length = n photons and the `.bur`/summary are unaffected). With no search (`filter_active=False`) the interval is the selection directly. Pinned by `test_delta_macro_time_prefilters_the_burst_search` (+ `_keeps_bursts_in_original_index_space`).

**IRF & background from non-burst photons.** A confocal single-molecule measurement is mostly empty focus, so the photons a burst search *rejects* are the built-in scatter/background: dark counts (flat in micro-time) plus scattered excitation light (a prompt peak = the IRF). `chisurf/core/fluorescence/burst/irf_bg.py::extract_irf_background` isolates those non-burst photons (inverting the sliding-window burst search) and, per detector, fits the interphoton-time tail for the background rate (kHz, reusing `background.estimate_background_from_interphoton_times`) and histograms the non-burst micro-times, subtracts a robust flat dark-count floor (a low quantile) and normalises the remainder to a scatter-derived IRF. The IRF spans the full laser period for the detector's channels (a PIE micro-time window would clip the prompt) and is deliberately per detector — each colour has its own response, so no shared IRF silently replaces distinct detector responses. This removes the need for a separate scatter/buffer acquisition to obtain an IRF. It surfaces in the guided facade as `BurstWorkflow.estimate_irf_background(dataset, setup=…)` (a one-liner: select bursts → read IRF/bg off the rejected photons) and `Bursts.irf_background()` (reuses the selection's burst-search parameters, pools non-burst photons across all loaded files); both return an `IrfBackground` with `.background_khz`, a per-detector `.table`, `.irf(name)`, and `.plot()`. Headless coverage: `test/plugins/burst/test_irf_background.py`; worked example: `examples/burst_irf_background.py`.

The **GUI** is the new-style AutoForm + JSON plugin `burst_irf_bg` (`Spectroscopy:Single-Molecule:Burst IRF & Background`, `menu_hidden`): a Qt-free `IrfBackgroundViewModel` drives the shared detector channel-definition page, a drop file list, the burst-search + dark-count-floor + micro-time-binning parameters, a per-detector IRF plot and a results table, all laid out from `gui/irf_bg.view.json` (mirrors `tttr_count_rate_analysis`). It is embedded in the `burst_analysis` navigation shell as the "IRF & Background" step (inheriting the shared channel definitions and selected raw files via the workflow context), and **feeds the burst MLE**: a `extract_mle_irf_background` core helper builds the vv_vh-stacked `[parallel, perpendicular]` (`chs[::2]` / `chs[1::2]`) micro-time patterns the MLE consumes, and the tool's "Send to MLE" action calls the shell's `apply_irf_background_to_mle`, which writes each detector's `irf_np`/`bg_np` directly (not through the file-drop loaders) and refreshes the decay/fit — so the non-burst scatter/background becomes the MLE-Lifetime fit's IRF and background with no separate acquisition. Headless coverage: `chisurf/plugins/burst/burst_irf_bg/test/test_widgets.py` (view-model compute + vv_vh patterns + widget construction, screenshot-verified) and `test/plugins/burst/test_irf_bg_workflow.py` (shell panel wiring + MLE handoff).

Each plugin is discovered through its `manifest.json` (`id`, `display_name`, `categories: [Spectroscopy, Single-Molecule]`) by the plugin infrastructure in `chisurf/core/plugin/`; `bid_to_analysis` is a code-only helper without a manifest. Plugins receive datasets, fits and project state through `PluginContext` / `ChiSurfAPI` rather than the legacy process globals, and their GUIs are rendered from AutoForm view schemes. The integrated windows (`burst_analysis`) build on the shared `NavigationPanelTool` shell. Its steps are Data Selection → Burst Selection → BVA → 2CDE → MLE-Lifetime → H2MM → Browser (+ Background and IRF & Background); a **Next ▶ / ◀ Back stepper** in the status bar walks the non-separator steps. There is **no standalone Channels step**: the channel/detector definition comes from the saved detector setup the Burst Selection step selects (`show_channel_selection=True`), published through the shared `detector_setups.*` RPC store and read back into the workflow context (`_sync_channel_context` → `_channel_settings_from_selection`). The workflow **carries the analysis folder** to every downstream step (`_apply_context_to_downstream` roles include `bva`/`two_cde`/`mle`/`h2mm`), so a step never re-asks for it. The shell owns **one shared status bar** — a distraction-less replacement for the per-tool modal progress popups: `begin_task(message, maximum, cancel=)` returns a `_StatusTask` handle (`chisurf/gui/widgets/navigation.py`) that renders into the bar's message + inline progress + Cancel and **duck-types the old popup dialog API**, so embedded tools obtained it via `find_status_reporter(widget)` instead of popping a dialog (BVA/`_begin_progress`, H2MM/`_make_progress`, MLE/`_mle_progress`); standalone tools keep their own dialog. Status **is reported by normal logging**: the shell installs a `_StatusLogHandler` scoped to `chisurf.plugins.burst`, so any `logger.info(...)` from a burst tool shows in the bar (worker-thread-safe via the `status_logged` signal; the handler updates only the caption and a task's close keeps the last message, so a final "Done – N bursts" survives). Action buttons across tools share one language via `chisurf/gui/widgets/tool_buttons.py` (`styled_tool_button` / `BTN_STYLES` — BVA's colour-coded scheme promoted to shared), and are **space-efficient**: emoji-only captions with the detail in tooltips. Step-1 Data Selection hosts the shared AutoForm `path_list` widget (drag-drop + ➕ Files / 📁 Folder / 🗄 Database / ➖ Remove / 🗑 Clear), bound via a small `_FileListModel` adapter that keeps the canonical `list[Path]`, imports newly-added local files to MMFDB, and exposes `paths()`/`mmfdb_payload()` to the workflow context.

`burst_2cde` computes the model-free **2CDE** dynamics feature (Tomov et al., BJ 2012) — a per-burst quantity, not a filter: it *computes* values and downstream code (e.g. ndX) selects bursts on them. **FRET-2CDE** = `110 − 100·[(E)_D + (1−E)_A]` is ~10 for static bursts and rises (30..100) under ms FRET dynamics; **ALEX-2CDE** = `100 − 50·[BR_Dex − BR_Aex]` flags acceptor blinking / D-only or A-only contamination in ALEX/PIE data. Both are built from per-photon kernel-density estimates (Laplace 5τ, or Gaussian 3τ) of two photon streams, computed on the *full* stream then sliced per burst (avoiding burst-edge artefacts). The heavy compute is the new tttrlib **`BurstFeature`** family: a base class (named photon streams by channels + inclusive micro-time windows, an optional bit-exact Laplace/Gaussian KDE, and a parallel per-burst reducer) with **`TwoCDE`** (FRET + ALEX variants) as the first feature and **`BVA` migrated onto the same base** (no hard-coded default channels; streams set explicitly). The C++ is a bit-exact port of the FRETBursts reference, parity-tested against a NumPy reimplementation. ChiSurf's `burst_2cde/core/computation.py` drives `tttrlib.TwoCDE` (with a pure-NumPy fallback), exposes a `2cde compute` CLI and `burst_2cde.jobs.compute` / `.workflow.prepare` RPC services, and writes per-file `2c4/<stem>.2c4` companions (the `…4` burst-companion family, alongside BVA's `bv4/<stem>.bv4`) — named after the `.bur` stem so per-stem consumers join them. The GUI's Compute writes the companion too, so the per-burst 2CDE column shows up in the **Burst Browser** and in **ndXplorer** with no extra step. **Browser + ndX merge:** `chisurf/core/fio/fluorescence/burst.py::read_bur_with_companions(folder)` column-merges every `<analysis>/<ending>/<stem>.<ending>` sibling (bg4/br4/by4/bv4/td4/2c4, auto-discovering any `…4` folder) into the `.bur` table (they share the `2n+1` interleaved layout, aligned by row), and the browser loads through it; ndXplorer's own `io/reader.read_burst_analysis` already merges the `…4` family and now (a) has `2c4` in its default endings — unioned with any stale user settings, not shadowed by them, (b) detects single-column companions (its scorer previously ignored <2-column files, so a lone `FRET-2CDE` column was read headerless), and (c) drops only trailing *empty* companion columns rather than the real last one (`modules/ndxplorer`, committed there). It joins the guided facade as `Bursts.two_cde(donor, acceptor, tau=…, kernel=…, variant=…)` → a `TwoCde` result (`.mean_2cde`, `.dynamic_fraction(threshold)`, `.plot()`). Headless coverage: `chisurf/plugins/burst/burst_2cde/tests/test_2cde.py` (tttrlib-vs-reference parity for both variants + kernels, result dataclass, sidecars, workflow prepare) and tttrlib's own `test/python/twocde/`.

**Recurrence Analysis of Single Particles (RASP).** `chisurf/core/fluorescence/burst/recurrence.py` adds the slow-dynamics complement to the within-burst features: RASP (Hoffmann et al., PCCP 2011) correlates a burst with the bursts that *recur* shortly after it (the same molecule diffusing back into the spot), extracting ms..s conformational kinetics and sub-population inter-conversion that a single burst cannot resolve. `same_molecule_probability` computes `P_same(τ) = 1 − 1/G(τ)` from the burst-arrival-time autocorrelation (log-spaced lags, finite-acquisition edge correction) — the timescale over which a recurring burst is still the same molecule; `recurrence_efficiencies` / `recurrence_histogram` select an initial FRET sub-population and histogram the efficiencies of bursts recurring within a chosen time window against the overall histogram. It operates purely on the per-burst table (arrival time + proximity ratio; no photon access) and surfaces in the guided facade as `Bursts.recurrence(donor, acceptor)` → a `Recurrence` result (`.same_molecule_probability()`, `.recurrence_time(threshold)`, `.histogram(e_range, dt_range_s)`, `.plot()`). Headless coverage: `test/plugins/burst/test_recurrence.py` (Poisson-flat vs clustered-recurrence P_same, recurrence histogram recovering an inter-converting state, time-window selectivity, workflow handle).
