# Use case: running a measurement — simulated single-molecule acquisition

**Goal:** the workflow *before* every file-based workflow in ChiSurf. The user
sits at the instrument (or, here, at the built-in simulator), sets the sample
and optics, presses **Start**, and watches the measurement come in live — the
fluorescence decay building up per detector, the correlation curve settling on
its amplitude and diffusion time, the count-rate trace showing whether the
sample is at the right concentration — then stops on a photon or time budget and
picks the recorded photon stream up for a burst search, an FCS fit or a decay
analysis.

The same window drives real TCSPC hardware (Becker & Hickl, PicoQuant,
BrickMic) and the tttrlib `Sim*` photon simulator. Only the simulator can be
exercised without hardware, and it is also the intended way to *learn* the
workflow and to generate ground-truth data for the analysis workflows — which is
what this use case walks.

**Data:** none on disk. The measurement is generated by the built-in simulator:
Brownian diffusion of fluorophores through a Gaussian confocal focus with
N-state photophysics/FRET, anisotropy and CW/pulsed emission. Every parameter
maps onto tttrlib's `SimSystem` / `SimSpecies` / `SimGrid` / `SimIntegrator`
(the per-parameter help in `chisurf/plugins/core/acq/manifest.json` is the shared
source of truth for the GUI tooltips, the CLI, the Python API and the
`acq.simulation.run` RPC method).

## Steps

1. Open **Main ▸ Tools ▸ Acquisition** (📷) on the ribbon. An **Acquisition**
   dock appears on the left and five MDI windows open — *Acquisition –
   Fluorescence Decays*, *– Correlation Curve*, *– Count Rate*, *– Macrotime
   Plot* and *– MCS Trace*.
2. Open **Settings ▸ Acquisition** — this, not the dock, is where the
   measurement is configured. Set the **Output** folder for the recorded files,
   the **Chunk Size** (photons read per chunk, default 16384) and, if you want
   the simulation paced to wall-clock time, **Real-time Sim**.
3. In **Device Configuration** pick the **Active Device Type**: *Simulation*,
   *Becker-Hickl*, *PicoQuant* or *BrickMic*. The device's own setup form is
   embedded below the combo.
4. For *Simulation*, fill the embedded form: **Mode** (CW / pulsed), total
   **Photons** and **Photons/file**, the two RNG seeds, the per-species
   **Sample_brightness** table (`M` molecules in the box, `D` in µm²/ms, the
   per-channel brightness `G∥` / `G⊥` in kHz, and a **Decay …** button for the
   lifetime spectrum), **Kinetics** (the inter-state rate matrix), **Geometry**
   (box half-extents, focus waists `w0` / `z0`, integration step) and
   **Micro-time** (TAC channels, TAC resolution, laser period).
5. Back in the **Acquisition** dock set the stop conditions: **Time [s]** and
   **Nbr Ph [k]** (kilo-photons; either may be 0 to disable, but not both).
6. Tick which live readouts you want in the **Show** group: *Fluorescence
   Decays*, *Correlation Curve*, *Count Rate*, *Macrotime Plot*, *MCS Trace*.
7. Press **Start**. The device is initialised automatically ("Ready (auto-init
   on Start)"); the progress bar tracks whichever stop condition is closer and
   the LCD beside it shows the mean count rate in kHz.
8. Watch the readouts: the decay histogram per detector, `G(τ)` for the
   configured channel pairs, the count-rate trace in cps, the inter-photon
   macrotime differences and the MCS intensity trace. Each plot window carries
   its own controller (channel spin boxes, log-Y, update frequency).
9. Press **Stop** to end early, or let the stop condition fire.
10. Collect the result: the simulator writes the stream as split
    Becker & Hickl SPC-132 files (`m000.spc`, `m001.spc`, …) plus a
    `simulation_config.json` and `simulation_info.txt` recording every
    parameter, ready for the burst / FCS / micro-time workflows.

The simulator is also reachable headlessly, without the GUI, through the
`acq.simulation.run` RPC method and through
`python -m chisurf.plugins.core.acq --cli config … / run …`.

## Expected

- Pressing **Start** produces photons within a second, and the live plots grow
  continuously until a stop condition fires.
- The acquisition stops at the requested photon budget, not far past it.
- Every detection channel of the configured device appears in the decay window.
- The recorded files land in the folder the user configured.
- The decay window's time axis matches the configured TAC resolution and laser
  period; the decay falls with time.
- **Save Settings** writes the acquisition configuration to JSON and **Load
  Settings** reads it back.

## Observed (last run: 2026-07-28)

Driven headlessly (`QT_QPA_PLATFORM=offscreen`, arm64 env) against the real main
window: the tool was opened, the settings panel filled, **Start** clicked, three
acquisitions run to completion, **Stop** exercised, and the written SPC files
read back with tttrlib. Screenshots inspected: the dock, the main window, the
settings panel, and all five plot windows after a run.

**What works.** The physics is right and the recorded files are real. A default
run (1 species, `M = 50` in a 2 × 2 × 4 µm box, `D = 3 µm²/ms`, `w0 = 0.3 µm`,
`z0 = 2 µm`, `q = 50 kHz` per channel) produced a correlation curve with
`G(0) ≈ 2.2`, i.e. `N ≈ 0.75` occupancy — which is exactly `M · V_focus/V_box`
(≈ 1.0 µm³ / 67 µm³ × 50 = 0.75) — over a flat `G(∞) = 1.0` baseline. The count
rate held steady at ~3.6 kcps per channel (LCD 7.4 kHz total) and the MCS trace
at ~7 counts/ms, consistent with each other and with the photon total. The
written `m000.spc` reads back in tttrlib as a valid SPC-130 stream: 6956
photons, routing channels 0 and 8 (3448 / 3508 — the two detectors, evenly
split), micro-times spanning the full 0–4095 TAC range, and a
`simulation_config.json` beside it that records every parameter of the run. The
**Stop** button responded in 1.2 s. The embedded simulation form (screenshot
`03_settings_panel.png`) is the best-looking part of the tool: grouped,
foldable, with a per-species table and a decay editor behind a button.

**Where it goes wrong.** Every step *around* that healthy core misreports or
ignores what the user asked for:

- **The recorded files do not go where the user said.** The output folder was
  set in the settings panel *and* typed into the dock; the configured folder
  stayed **empty** and the files were written to a timestamped
  `simulation_output_<stamp>/` directory **relative to the process working
  directory**. In the first run that put **147 SPC files into the repository
  working tree**. Root cause is a two-line ordering bug (RF-810): the dock's
  path is written into `simulation_params["spc_output_path"]`, and the saved
  settings-panel snapshot — which carries `spc_output_path: ""` — is applied
  *after* it and blanks it again. The embedded form has its own, second, empty
  **Output folder** field, so there are three places to type a path and none of
  them wins.
- **The photon budget is not a budget.** With **Nbr Ph [k] = 20** (20 000
  photons) the run delivered **190 671**. The simulator generates the entire
  `N_ph_max` batch in one blocking call *before* streaming any of it, so the
  stop check fires 56 times in a row — "Photon limit reached (20,847 …)",
  "(24,315 …)" … "(190,671 photons)" — while the already-generated stream keeps
  draining (RF-812). In a second run with `N_ph_max = 40 000` and the same 20 kPh
  limit, exactly 40 000 photons came back.
- **Nothing happens for the first 23 s.** Because generation is up front, the
  default 1 000 000-photon run showed an empty screen and a progress bar reading
  `0 %` with no words for 23 of its 28 s, then delivered everything at once —
  fast enough to overflow the processing queue ("DataProcessingThread queue
  full, dropping chunk"), so the live plots are computed on a silently truncated
  subset. Meanwhile the status text the code sets ("Status: Acquiring data") is
  overwritten by `%p%` on the first progress tick and is never actually visible.
- **Half the photons are invisible.** The simulator's shipped `ch_conversion`
  puts the two detectors on routing channels **8 and 0**, but the decay window's
  channel mapping defaults to 0, 1, 2, 3 — so only channel 0 is histogrammed
  (93 458 counts of 187 207 photons) and the second curve sits flat at zero for
  the whole measurement (RF-816). The spin boxes that would fix it exist in the
  code but are not on screen.
- **The decay plot is wrong on both axes** (screenshot `06_decay.png`): the x
  axis is a hard-coded `linspace(0, 100)` ns regardless of the configured TAC
  resolution — the true span here is 4096 × 0.004069 ns = **16.7 ns**, so the
  axis is 6× too wide and sits well past the 13.6 ns laser period — and the raw
  inverted Becker & Hickl TAC is plotted as-is, so the fluorescence decay is
  drawn **rising** from 20 ns to 100 ns (RF-815). Confirmed against the file:
  the micro-time histogram genuinely peaks at TAC channel ~4032.
- **The dock hides its own controls.** The output-folder row and the
  **Save Settings** / **Load Settings** buttons are placed in the same grid cell
  as the **Show** group box, which is added last and covers them completely
  (RF-813, screenshots `01_dock.png` / `05_dock_after_run.png`). The device-type
  combo is constructed but never added to any layout at all (parent `None`,
  `isVisible() == False`), and the **Simulation Setup…** button never unhides
  because the check compares the device's `"SIMULATION"` against the literal
  `"Simulation"` (RF-814). The visible dock is therefore four widgets wide:
  Time, Nbr Ph, Start, Stop — plus five checkboxes.
- **Save Settings raises.** `_get_current_settings()` reads
  `acquisition_dock.chunk_size`, an attribute the dock never defines →
  `AttributeError` (RF-811). The button is occluded, so this has never been hit
  from the UI.
- **Photons/file is silently overridden.** The Simulation Setup's
  *Photons/file = 100000* was replaced by the *Chunk Size* advanced setting: a
  40 000-photon run with chunk 5000 produced eight 5000-photon files, and the
  `simulation_config.json` written beside them records `N_ph_per_file: 5000`
  (RF-817).
- **The documented command-line entry points do not start.**
  `python -m chisurf.plugins.core.acq` and `--standalone` both die with
  `ModuleNotFoundError: No module named 'chisurf.plugins.core.acq.main'`
  (RF-818).
- Two further things a user would notice and this run could not fully pin down:
  the correlation curve's half-decay reads ≈ 0.03 ms against an analytic
  `τ_D = w0²/4D = 7.5 µs` for the configured optics (read off the plot, not
  fitted — worth a dedicated check before trusting the simulator's absolute
  timing), and the *Macrotime Plot* / *MCS Trace* windows draw their controller
  labels ("Display Only", "Update Freq", "Y Range") on top of the MDI title bar
  text (screenshots `06_macrotime.png`, `06_mcs.png`).

## UX / UI suggestions

- **One place to say where the data goes.** There are three output-folder
  fields — the settings panel's *Output ▸ Folder*, the embedded simulation
  form's *Output folder*, and the dock's *Output folder* — for one destination.
  Keep the settings-panel one, drop the other two, and show the resolved
  absolute path back to the user after a run ("wrote 145 files to …") instead of
  only in the log.
- **Say what the run will cost before it starts.** *Photons* (`N_ph_max`),
  *Photons/file*, the dock's *Nbr Ph [k]* and *Time [s]*, and *Chunk Size* are
  five interacting budgets spread over two windows. A single line under Start —
  "1 000 000 photons ≈ 25 s of measurement in 145 files" — would make the
  relationship visible; today the only way to learn that *Photons* dominates
  everything is to run it.
- **Show progress during generation.** Even if the simulator cannot stream, the
  generation phase should own the progress bar ("Simulating 1 000 000
  photons…") rather than leaving `0 %` with no text for 23 s.
- **Label the count-rate LCD.** It reads `7.4` with no unit and no channel; the
  plot beside it says "cps" while the LCD is kHz.
- **Give the dock its controls back**: the device type, the *Simulation Setup…*
  button, the four detector-channel spin boxes and the output folder are all
  constructed and all unreachable. The four channel spin boxes in particular are
  what a user needs the moment the second detector's decay stays flat.
- **Open the five plot windows tiled, not stacked.** All five are added at the
  same MDI position and shown in sequence, so only the last one is visible and
  the other four have to be dragged out from under it.
- **`M = 50` is not a single-molecule default** for a tool called *Single-molecule
  fluorescence acquisition*; the RPC schema's own default is `1.5`. Ship the
  schema default, and label the units in the species table header (`D` µm²/ms,
  `G∥`/`G⊥` kHz), which today carries bare symbols.
- **The README describes a different tool**: it documents an "Initialize the
  device" step, a blue *Help* button and "save the data when the acquisition is
  complete". There is no init button (auto-init on Start), no Help button, and
  `_save_data()` is an empty `pass`.
- **Nothing carries the measurement forward.** The recorded stream is left on
  disk for the user to find; an "Add to ChiSurf" / "Open in Burst Analysis"
  action at the end of a run is the obvious next click and does not exist.

## Bugs filed

- RF-810 — the configured output folder is overwritten by the settings snapshot,
  so recordings land in the process working directory.
- RF-811 — **Save Settings** raises `AttributeError` on a dock attribute that
  does not exist.
- RF-812 — the photon stop condition overshoots by up to 10×; the whole
  `N_ph_max` batch is generated and written regardless.
- RF-813 — the dock's output-folder row and Save/Load Settings buttons are
  covered by the *Show* group box.
- RF-814 — the device-type combo is never laid out, and the `"SIMULATION"` vs
  `"Simulation"` mismatch keeps *Simulation Setup…* hidden and rebuilds the
  device on every Start.
- RF-815 — the live decay is drawn on a hard-coded 0–100 ns axis and with the
  raw inverted TAC, so it rises with time.
- RF-816 — the default channel mapping misses the simulator's routing channels,
  so half the photons never reach the decay window.
- RF-817 — *Photons/file* is silently replaced by the *Chunk Size* setting.
- RF-818 — `python -m chisurf.plugins.core.acq [--standalone]` fails on a
  missing `.main` module.
