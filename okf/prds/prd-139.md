# PRD-139 — Should the IMP build of imp.bff leave IMP's in-tree tooling?

**Status**: open question (2026-09-08), raised by the owner while reviewing
PRD-137. Not scheduled.

## The question

`imp.bff` is built today by IMP's own module tooling: the sources sit in
IMP's tree as a module, `dependencies.py` names the modules, and generated
CMake files do the rest. IMP also supports being used as a plain library
([manual](https://integrativemodeling.org/2.25.0/doc/manual/uselibrary.html)):
an external CMake project calls `find_package(IMP)` and links
`IMP_<module>_LIBRARY` with `IMP_INCLUDE_DIR` on the path, with none of that
tooling. `standalone/CMakeLists.txt` (PRD-137) already builds these sources
by itself. Should it grow an `IMPBFF_WITH_IMP` configuration that builds
core **and** connection layer against a pre-built IMP, and become the one
build system for both packages?

## What it would buy

Every one of these exists only because IMP's tooling has to be satisfied:

- headers must be flat (`setup.py link_headers` links `include/*.h` and
  `include/internal/*.h` and nothing else), so the layer's headers sit
  beside the core's and are listed in `src/imp/Headers.cmake`;
- the unity file compiles only `src/*.cpp` and `src/internal/*.cpp`, so the
  layer is reached through the flat bridge `src/ImpLayer.cpp`, which
  `#include`s the layer's sources;
- `src/Files.cmake` is tracked and regenerated by hand;
- `dependencies.py` decides the module closure, and the RMF entry cannot be
  dropped in-tree because of configure ordering (PRD-137 step 3).

With its own CMake, `src/imp/` becomes an ordinary subdirectory with
ordinary headers, and one `CMakeLists.txt` serves both packages, switched by
a flag.

## What is measured, and what is not

**Measured (2026-09-08).** The core's headers compile against real IMP with
no shims. A hand-rolled IMP-mode unity build compiled 83 of 84 sources; the
single failure was `IMP_WARN` in `src/PathMap.cpp` expanding to nothing,
which is a logging-flag difference between the hand-rolled command and
IMP's own, not a design problem. (The 84th, `src/Pto.cpp`, was another
agent's in-progress file.) A library cannot mix the two worlds: the shim
tree and IMP's headers redefine `IMP::Exception`, `IMP::Object`,
`IMP::Pointer` and `IMP::algebra::VectorD`, so a translation unit holds one
or the other.

**Not measured, and the real risk: the Python wrapper.** The layer's
signatures are IMP-typed (`IMP::atom::Hierarchy`, `IMP::Model`), so SWIG
needs IMP's own interfaces (`IMP_SWIG_DIR` ships them) and the generated
module has to integrate with IMP's Python the way `imp_build_module` makes
it: shared exception classes, the director registry, IMP's typemaps.
`npctransport` builds an IMP module out of tree, so it is known-possible;
whether it is *cheaper* than the tooling is exactly what this PRD would
have to establish.

## Does WebGPU bear on this? No -- withdrawn the same day (2026-09-08)

Recorded because the wrong version of this argument is tempting and was
written here for a few hours.

**The claim was**: `gpu/imp_bff_wgpu.c` builds a *second shared library*
beside the extension, and IMP's module tooling cannot express one -- the
`modules/*/CMakeLists.txt` files are generated from
`tools/build/cmake_templates/Module.cmake` and say "Do not edit - any changes
will be lost", no module in the IMP tree declares an `add_library` of its own,
and a module gets `src/`, `bin/`, `test/`, `examples/`, `benchmark/` and
`pyext/` and nothing else. Therefore, it said, the GPU path can exist in the
`bff` wheel and not in the conda `imp.bff` module package -- a capability
asymmetry that only this PRD could close.

**The premise is true and the conclusion does not follow.** It confuses
building with shipping. The plugin is one C file, 67 KB compiled, that links
nothing but libc (`otool -L`: libSystem, and that is all), and it is located
**by path at run time** -- nothing links it, and every wgpu entry point is
resolved by `dlopen`. IMP's tooling therefore never has to know it exists. The
*recipe* compiles it in one command and drops it beside the module, which
`conda-recipe/build.sh` and `bld.bat` now do, and `IMP.bff.enable_gpu()` finds
it there exactly as it does in the wheel. Verified by building into a prefix
and loading the result.

So there is no asymmetry, and **WebGPU is not an argument for this PRD in
either direction.** The generalisation worth keeping is small and had been
guessed at rather than tested: an artifact that must be *linked* into the
module, or must participate in its build, would still be impossible in-tree.
A run-time plugin is not that, and neither are most useful things -- so this
does not become an argument until something concrete needs it.

## The bigger version of the question: embed IMP in the wheel

"IMP has no wheel" is not the obstacle it looks like. A wheel does not need
IMP's *Python package*; it needs IMP's *C++ libraries*, and a wheel can carry
those the way this project's wheel already carries librmf, Boost and libicu:
built in cibuildwheel's `before-all` (the shape `utility/wheel_deps.sh`
already has for RMF, which has no wheel either) and vendored by
`delocate`/`auditwheel`. Measured 2026-09-08:

- the module closure bff needs -- kernel, algebra, atom, core, container,
  em, rmf, rotamer, display, score_functor, statistics -- is **13.9 MB** of
  shared libraries, and `IMP_DISABLED_MODULES` trims the rest;
- `libimp_kernel` links **no** Python (`otool -L`), and IMP's `CMakeLists.txt`
  guards every `pyext` subdirectory with `if(NOT IMP_STATIC)`, so IMP's
  Python wrappers can be left out of such a build entirely;
- dynamic bundling keeps this LGPL-clean, and it is what the wheel tooling
  does anyway.

The one hard condition: **the Python surface must stay IMP-free**. The moment
a wrapped signature names `IMP::atom::Hierarchy` or `IMP::Model`, SWIG needs
IMP's own `.i` files and the extension imports `_IMP_kernel` at module init
(`IMP_kernel.exceptions.i:52`), which drags IMP's Python package into the
wheel. Expressed as arrays and file paths -- the doors this project already
prefers -- nothing of IMP appears in Python, and the dye Langevin road works
in a plain `pip install bff`.

**And then the shims are not needed.** If every shipped configuration links
IMP (embedded in the wheel, depended on in conda), `standalone/include/IMP/`,
Base.h's second branch and the two-lane test hook all go away, and there is
one build with one set of headers. That is the simplification the owner asked
about, and it is real -- at the price that every bff user carries IMP's code,
that CI builds IMP per platform, and that the "links no IMP" property, which
was PRD-137's premise, is given up.

## What this does not change

The shims stay only if a genuinely IMP-free build is still wanted -- a small
library that links nothing of IMP, which is what PRD-137 set out to make. The
de-IMPing itself (array doors, the core's own PDB/MOL2 readers, the MRC
writer, `get_av` without a Model) keeps its value either way: it is what lets
the same sources build in both worlds.

## The decision this actually poses

1. **Two worlds, as today** -- shims for the IMP-free package, IMP's tooling
   for `imp.bff`. Langevin stays IMP-only. Nothing to do.
2. **Two worlds, one build system** -- keep the shims, add
   `IMPBFF_WITH_IMP` to `standalone/CMakeLists.txt`, retire IMP's in-tree
   tooling. Langevin still needs IMP installed.
3. **One world** -- every configuration links IMP (embedded in the wheel,
   depended on in conda), the shims are deleted, and everything works
   everywhere, including Langevin.

## Measured end to end (2026-09-08)

The owner chose the embedded, minimal IMP and asked for the numbers before
the machinery. All of this is on an M-series Mac, from this project's own
`standalone/CMakeLists.txt`:

| | |
|---|---|
| IMP modules the layer names | atom (284 uses), core (193), algebra (202), container (13), em (3), rotamer (3) |
| ... and nothing else | no rmf, isd, saxs, display, statistics in layer code |
| the core's IMP mentions | comments only, in every file checked |
| required libraries | kernel, algebra, display, score_functor, core, container, atom — **10.1 MB** |
| the two narrow spots | em + statistics + rotamer — **1.4 MB** for `create_density_map` and the Dunbrack placement |
| minimal IMP build | **57 s wall**, ten modules, libraries only, no SWIG, nothing linked against Python |
| `libimp_bff` with the layer | **6.4 MB**, built in **71 s** against that IMP |
| IMP source needed to build it | 95 MB (ten modules + tooling); IMP's tooling lives in RMF's submodule |

`standalone/CMakeLists.txt` now carries `IMPBFF_WITH_IMP`: off, the shims
stand in and only the core is built; on, IMP's headers replace the shims,
`src/imp/` is compiled in, and the library links the modules above. The
switch is exclusive by nature -- the two vocabularies cannot share a
translation unit. Two small things had to give: `Base.h`'s IMP branch now
includes `<IMP/log_macros.h>` (its `IMP_WARN` was undefined, so the macro's
stream argument was compiled as an expression), and `bff_config.h` defines
`IMPBFF_STANDALONE` only when `IMPBFF_WITH_IMP` is absent, so one config
header serves both. `utility/wheel_deps.sh` builds the minimal IMP behind
`WITH_IMP=1`.

Verified: the layer's symbols are in the library (`make_langevin_simulator`,
`attach_probes`, `place_probe`, `AttachedProbeDynamics`, `prepare_particles`,
`create_density_map`), and the IMP-free build still passes its lane 724/0.

## The Python surface, and the dye Langevin road (2026-09-08)

Done, and it runs. `IMP.bff.attach_dye_to_pdb` and
`IMP.bff.run_dye_langevin` (`include/DyeDynamics.h`,
`src/imp/DyeDynamics.cpp`) are the connection layer's dye roads behind file
paths and arrays: the model, the two hierarchies and the particle indexes
are made inside and die inside. Measured on a build with the embedded
minimal IMP: a real trajectory, 5 frames of 83 atoms with its energies,
from a Python where `IMP.atom` is **not importable**.

The rule that makes it work: **nothing wrapped may name an IMP type.** A
wrapped `IMP::atom::Hierarchy` makes SWIG need IMP's own `.i` files, and the
extension then calls `PyImport_ImportModule("_IMP_kernel")` at load
(`IMP_kernel.exceptions.i:52`) -- IMP's Python would have to be in the wheel.
Behind paths and arrays none of that follows. So the layer keeps its
IMP-typed API for callers who have IMP, and these two doors are what a wheel
offers.

What it took beyond the doors themselves, all of it in the standalone SWIG
entry and its macros:

- SWIG cannot parse `Base.h` in this configuration (it forwards to IMP), so
  it is handed the macro expansions instead -- and they must be **IMP's**
  spellings: `IMP_VALUES` makes an `IMP::Vector<T>`, not a `std::vector<T>`,
  and a typemap written for the wrong one assigns across incompatible
  pointer types.
- `IMP::Vector<T>` therefore gets the same value typemaps as `std::vector<T>`
  (`IMP_SWIG_VALUE_VECTOR_TYPEMAPS`), and `VectorD` is declared under both
  the `IMP::` and the `IMP::algebra::` spelling, because headers use both and
  SWIG matches typemaps on the spelling it sees.
- A value return arrives as `SwigValueWrapper`, so the vector `out` typemap
  binds a reference before touching it.
- IMP's `VectorD` calls `boost::distance` in a constructor template and gets
  the declaration from headers this translation unit does not include, so the
  wrapper includes `<boost/range/distance.hpp>` first.
- The director registry may not ask for `get_ref_count` before holding a
  Python subclass: `IMP::Object` is not wrapped here, so the attribute is
  absent, the registry held nothing, and a cancelled minimizer run segfaulted
  on a collected observer.
- IMP reads its own data at run time (`IMP::atom`'s `top.lib`, `par.lib`),
  which a wheel has to carry: 3.1 MB, against the 18 MB of `score_functor`'s
  statistical potentials that these roads never open.

`IMP.bff.get_build()` now has three answers: `core`, `core+imp`, `imp`.
`test/test_dye_dynamics_doors.py` covers it and, on a `core+imp` build,
asserts in a subprocess that running a dye imports no IMP module. The lanes
agree: 724/0 on the IMP-free build, and in one environment the IMP-linked
build differs from it only by the new tests.

## One shape for every simulation (2026-09-08, owner's review)

The first cut of those doors was two free functions taking PDB paths, and
the owner refused both halves: a path is a file format where an array
belongs, and a one-shot function is not how anybody drives a simulation.
"Setup a simulator, with parameters, then run, programmatically, like in
OpenMM." Then, on seeing it: make it general enough for Langevin, MD,
diffusion, lattice diffusion and a learned model, "maybe json style". And:
generalize `ProbeDiffusionSimulation` onto the same interface.

`include/Simulation.h` is that shape, in the core:

- `SimulationTrajectory` -- the module's one trajectory record now, shared by
  every simulation. `LangevinTrajectory` is a typedef of it.
- `ProbeSimulation` -- `get_type()`, `get_parameters()` / `set_parameters()`,
  `get_positions()` / `set_positions()`, `minimize()`, `step()`, `run()`,
  `get_potential_energy()`, `has_energy()`.

**Parameters are JSON, and that is what makes one interface possible.** A
Langevin run wants a temperature, a timestep and a friction; a grid walk
wants a diffusion coefficient, a slow factor and a voxel edge; a lattice walk
wants a stencil; a learned forward model wants weights. In one struct, every
simulation would carry every other's fields and adding a kind would move
everybody's arguments. A JSON object says only what this simulation has,
`set_parameters` takes a partial one, `get_parameters` reports what is in
force -- which is also what belongs in a file beside the results -- and an
unknown key is refused by name rather than ignored. State and system stay
arrays: coordinates, grids and topologies are large and numeric, and JSON is
neither.

Two implementations today:

- `DyeSimulation` (layer): a `ProteinFrame` for the structure and one for the
  dye -- arrays, no PDB anywhere in the signature -- plus the dye's MOL2 for
  its chemistry, because that is a chemistry file and coordinates cannot
  replace it. Everything of IMP is behind a pimpl, so the header names none
  of it. Its parameters are fixed once the system is built and it says so
  rather than reporting one thing and integrating another.
- `ProbeDiffusionSimulation` (core): the grid walk, now a `ProbeSimulation`.
  Its old `run(D, slow_fact, t_step, t_max, n_trajectories, seed)` became
  `simulate(...)` so that `run(n_steps, write_every)` could mean what it
  means everywhere else; the parameters it used to take positionally are the
  JSON ones.

The array-to-hierarchy bridge this needed --
`hierarchy_from_protein_frame`, the inverse of the existing
`protein_frame_from_hierarchy` -- is in `HierarchyBridge.h`, and is what lets
any caller with coordinates in memory reach IMP's machinery without writing
a file first.

Measured: the same six lines of Python drive both simulations to a
trajectory, `isinstance(sim, ProbeSimulation)` holds for both, and an
unknown parameter is refused by name.

## What the wheel weighs, and where the weight was (2026-09-08)

The owner asked whether the embedded build is fat, and it was -- but not
where it looked. Measured on a repaired macOS arm64 wheel:

| | before | after |
|---|---|---|
| wheel | 20.66 MB | **5.42 MB** |
| bundled libraries | 45.0 MB | 1.9 MB (libc++, libomp) |
| ICU (icudata + i18n + uc) | 34.8 MB | gone |
| libhdf5 | 3.8 MB | gone |
| librmf | 3.2 MB | gone |

Three findings, in order of weight:

1. **ICU rode in on RMF.** librmf links Boost.Iostreams, and Boost.Iostreams
   as packaged -- conda-forge *and* Homebrew alike, checked -- links
   Boost.Regex, which links all of ICU. 35 MB for a file format most callers
   never open.
2. **RMF is peripheral.** `RMF::` appears in exactly one source file
   (`src/RmfIO.cpp`, 93 uses) behind four public functions, and the only
   callers in the tree are two commands of `bin/imp_bff`. Nothing in the
   library calls them, and the whole test lane passes without them: 724/0.
   Hence `IMPBFF_WITH_RMF`, opt-*out* so IMP's own tooling keeps building
   what it always built; the wheel turns it off, conda keeps it.
3. **HDF5 rode in on RMF too**, and was already fixed by building RMF with
   its deprecated backends off (`utility/wheel_deps.sh`).

Two smaller things fell out. `install.strip` is back on -- safe because the
install re-signs the binaries afterwards, which is what arm64 macOS needs --
and RMF's own build leaves each dylib's install name pointing into the build
directory, so `wheel_deps.sh` now fixes it; without that anything linked
against a hand-built RMF fails at import with "Library not loaded", which a
wheel hides only because delocate rewrites it.

Hidden visibility was tried and **reverted**: it saved 0.23 MB and broke four
tests, because the typeinfo of the exception classes stops being exported and
the `catch` that translates them lives in the extension while the `throw` is
in the library. Marking every thrown type visible would buy it back.

What is left in the 5.42 MB: the SWIG extension (7.2 MB uncompressed), the
core library (4.1 MB), the shadow module (0.9 MB), the small data (2.2 MB),
and libc++ + libomp. The conda libc++ is a local artifact -- a CI wheel built
against the platform toolchain will not carry it.

## Suggested first step

Add `IMPBFF_WITH_IMP` to `standalone/CMakeLists.txt` for the **C++ library
only** (no Python), and check that `libimp_bff` built that way is
functionally the IMP module's library: same symbols, same test results
through the existing IMP-built Python module. That settles the C++ half
cheaply and leaves the wrapper question standing on its own.
