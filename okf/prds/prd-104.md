# emtk — ImPlot, ImPlot3D and a view gizmo, drawn through chimol's own painter

# Where to pick this up

**2026-08-13 — foundation phase.** User asked to port ImPlot, then ImPlot3D,
then ImViewGuizmo into chimol's toolkit, named `tk`/`emtk` — the name expands
to **Canvas Model Toolkit** (2026-08-14; renamed to emtk, Embeddable iMmediate-mode ToolKit, 2026-09-16) — with references mined into `junk/`
per the standing rule. Chimol independence comes first: ChiSurf reaches emtk
**via chimol**, and the ChiSurf↔emtk interface is still floating (2026-08-14).
**2026-09-17 — Phase 3 done** (emtk `6c92827`, `07c5efd`). Open: the demo's
popups draw inline after the plot (emtk popups are not floating windows); the
z-axis title can read top-to-bottom when the vertical edge's screen angle
rounds past 90° (the reference's upright rule, kept); a vertex-colour
triangle through QtPainter is subdivided, not exact.
See the "Where to pick this up"
section at the end of this file for the exact state of each phase — this PRD
is Draft because only the foundation and a first vertical slice can land in
one session against a ~21.7k-line combined reference (implot 12.6k,
implot3d 8.5k, ImViewGuizmo 0.6k lines of C++).

## Why

[`chimol-viewport-ui.md`](../plugins/chimol-viewport-ui.md) already ports Dear
ImGui's *widget* stack into `chisurf/plugins/chimol/chimol/emtk/` —
sliders, buttons, tables, menus — drawn through a deliberately minimal
`Painter` protocol (`fill_rect`, `stroke_rect`, `gradient_rect`, `text`,
`push_clip`/`pop_clip`; [`docs/development/chimol_widget_toolkit.md`](../../docs/development/chimol_widget_toolkit.md)
calls this "the largest set a triangle rasteriser serves directly"). ImPlot and
ImPlot3D are the natural next layer — the same author's (Evan Pezent) plotting
library built on top of Dear ImGui — and a view-manipulate gizmo is the
standard companion widget every 3-D viewport with an orbit camera grows.
chimol currently has neither: `frame_stats.py`'s "nerd mode" graphs
(`internal_gui.py:4805` `_paint_nerd_graph`) are bar sparklines built from
`fill_rect` calls, and `widgets.PlotLines` staircases a polyline into columns
— both explicitly *substitutes* for a line primitive the painter does not
have, chosen because a sparkline is small enough that the substitution is
"indistinguishable ... at sparkline sizes" (`widgets.py:1004-1006`). A real
plot area is not sparkline-sized, and none of ImPlot's marker shapes (circle,
diamond, cross, plus) or ImPlot3D's triangle-mesh surfaces are expressible as
axis-aligned rectangles at any size.

## The one architecture decision this PRD makes

**Add exactly one primitive to `Painter`: an arbitrary filled triangle.**

```python
def fill_triangle(self, p0: tuple[float, float], p1: tuple[float, float],
                   p2: tuple[float, float], colour: Colour) -> None: ...
```

Not a line, not a polygon, not a rotated rect — a triangle, because:

* it is what `quad_painter.py`'s own docstring already names as the floor
  ("six operations that a triangle rasteriser can serve directly") — every
  existing `fill_rect` is already two triangles at the vertex-buffer level
  (`_TRIANGLES = np.array([0, 1, 2, 0, 2, 3])`, `quad_painter.py:74`); this
  generalises the *shape* of the two triangles a rect already emits, not the
  pipeline;
* one primitive serves every new caller: a diagonal line segment is a thin
  triangle pair (`line(x0,y0,x1,y1,width,colour)` becomes a two-triangle
  helper built on `fill_triangle`, so `Painter` itself grows only one new
  method, `line`, implemented once in terms of `fill_triangle`); a scatter
  marker (diamond, cross) is two-to-four triangles; a gizmo cube face is a
  perspective-projected quad, i.e. two triangles with independent corners; an
  ImPlot3D surface/mesh literally *is* a triangle list;
* it is additive, not a violation of the existing floor's design intent. The
  floor's stated exclusions (`chimol_widget_toolkit.md` "What is not here") are
  `Image`/`ImageButton` (no image op — untouched by this), the colour wheel
  (an annulus — untouched), Box-Select (a differencing algorithm — untouched)
  and keyboard-nav/docking/`.ini` (global-context features — untouched). None
  of those reasons apply to a triangle; the floor simply had no caller that
  needed one yet.

Both existing `Painter` implementations gain it:

* **`qt_painter.py`** — `QPainterPath` with three `lineTo`s, `NoPen`/solid
  brush, matching every other method's "closed path, fill, no outline unless
  asked" style already used by `fill_rect`.
* **`quad_painter.py`** — a **second, parallel accumulation list**
  (`self._tris`), not a detour through `vertices()`'s existing rect-corner
  expansion (`corners[:, 0, 0] = corners[:, 3, 0] = left`, `quad_painter.py:224-231`,
  which is *derived from* `x, y, w, h` and has no way to hold three
  independent corners). Each triangle is 3 vertices of the same 12-float
  format (`position, uv, colour, box`), with `uv` pointing at the atlas's
  known-opaque texel — identical to how a rect quad is flat-shaded today — so
  `ui.wgsl` needs no new pipeline, only a longer vertex buffer. `vertices()`
  concatenates the expanded rect corners with the raw triangle vertices before
  return.
* **`test/test_ui_widgets.py`'s `RecordingPainter`** — records `("triangle",
  p0, p1, p2, colour)`, mirroring how it already records `("fill_rect", ...)`.

Parity between the two implementations is asserted the same way
`qt_painter.py`'s module docstring already requires for the rest of the
protocol ("byte-identical ... a test asserts it").

## Phases

**Phase 0 — foundation (this session).** Reference checkouts (`junk/implot`,
`junk/implot3d`, `junk/ImViewGuizmo`, registered in `junk/clone.sh`), this PRD,
the `fill_triangle`/`line` primitive on both painters + `RecordingPainter`,
parity test.

**Phase 1 — emtk 2D core (landed this session).** New package
`chisurf/plugins/chimol/chimol/emtk/`. A builder API close to
ImPlot's call shape (`begin_plot` returns a `Plot` used as a context manager,
since Python has no RAII destructor to lean on the way `ImPlot::EndPlot` does)
but not literally immediate-mode: items are recorded by `Plot.line`/
`Plot.scatter`/`Plot.hline` and the frame, gridlines, items and legend are all
drawn together on `__exit__`/`Plot.draw`, because chimol's plots are rebuilt
from scratch every call with no previous frame's fitted range to draw
against, unlike ImPlot's persistent per-plot context. Linear axes with
auto-fit (`axis.py`, the one piece of arithmetic every plot type shares,
ported from `ImPlotAxis`'s `PixelsToPlot`/`PlotToPixels`), "nice number"
ticks (Heckbert's algorithm), 4 marker shapes (`markers.py`: circle via the
existing `style.disc`, square/diamond/cross new), a legend. Verified with a
headless screenshot, inspected directly — see
[chimol-emtk.md](../plugins/chimol-emtk.md) for what it showed.
`_paint_nerd_graph`'s bar sparklines for the non-stacked series (fps, frame
time, cpu load, submitted instances) **are replaced** by real `emtk.begin_plot`
line plots — the first production caller, and the point the port existed to
reach; the stacked "frame time, in detail" breakdown stays bars (Phase 2).

**Phase 2 — emtk 2D breadth (open).** Bar/stem/shaded/error-bar/stairs/
histogram/heatmap plot types — each is a straightforward reuse of the rect or
triangle primitive, no new architecture. Digital signals, pie charts,
candlestick, drag-lines/drag-points, colormaps, subplots grid, mouse-driven
pan/zoom/box-select-to-fit (ImPlot's own hallmark interaction). Axis
log/time/reversed scales. Not started.

**Phase 3 — emtk3d (done 2026-09-17).** ImPlot3D (brenocq/implot3d at
6cbefa9) ported whole into the standalone emtk repo (`~/dev/emtk`, not chimol
— the old `cmtk`-in-chimol paths above are historical): `emtk/implot3d.py`
(`implot3d.h` + `implot3d_internal.h` + `implot3d.cpp`),
`emtk/implot3d_items.py`, `emtk/implot3d_meshes.py` and
`emtk/implot3d_demo.py`. Correction to the plan above: the reference's meshes
are a **cube, an icosphere and a rubber duck** (no cylinder/cone, no
procedural tessellation — `PlotSurface` tessellates a grid); they are
*extracted* by `tools/port_implot3d_meshes.py`. The projection is the
reference's: quaternion rotation (as a 3x3 matrix, same linear map), NDC box
of ±0.5·scale, view scale `min(w,h)/1.8`. Items become screen triangles with
the reference's depth (rotated **plot-space** centroid — not NDC, a quirk
kept), sorted far→near at `end_plot`, drawn through `fill_triangle` plus two
new **optional** painter ops on every painter: `gradient_triangle`
(per-vertex colour; Qt subdivides) and `image_triangle` (affine texture).
Pure Python (emtk has no NumPy): 50×50 surface with grid lines ≈45 ms/frame
projection+sort (fill only ≈21 ms), painter excluded. Everything in the
public header and all 29 demo sections ported; skipped: ImGui's font atlas as
the Image demo's texture (a generated checkerboard stands in), clipboard/TTY
style export, ImGui's own windows in the demo menu. emtk `6c92827` (painter
ops; also fixed `PixelPainter.text_rotated`, `im_widgets._rotated_text`, a
zero `io.mouse_delta`), `07c5efd` (implot3d, 67 tests, gallery tool, docs,
CREDITS). No gizmo/ViewCube (Phase 4 stays removed).

**Phase 4 — ImViewGuizmo, then superseded by a ViewCube (redesigned
2026-08-13, later the same day).** Originally a corner-of-viewport
orientation gizmo ported faithfully from `ImViewGuizmo.h` (630 lines, single
header): six axis balls (`+X`/`-X`/`+Y`/`-Y`/`+Z`/`-Z`) plus a big invisible
centre disc that started an orbit drag. A reference screenshot showed this was
the wrong target entirely — the classic Blender/3ds Max/ChimeraX "ViewCube"
(a solid, lightly-shaded cube, labelled faces, darker edges, a small RGB axis
indicator at one corner) that the reference header itself said the port was
**not**. `emtk/gizmo.py` was rewritten outright to be that cube; the
axis-ball code is gone, not kept behind a flag. See
[chimol-emtk.md](../plugins/chimol-emtk.md)'s dated entry for the redesign for
the full geometry/interaction account and file:line citations.

What survived the rewrite: the projection maths. `_view` (one matrix-vector
product against `CameraState._rotation`) still needs no 4x4 matrices or
projective divide, generalised from 6 axis directions to the cube's 8 corners
(each just a sum of signed axes, and a rotation is linear). The six
hand-solved `(elevation, azimuth)` snap pairs (`AXIS_ORIENTATIONS`) are kept
as a literal regression target; a new `_orientation_for_direction` solves the
same equation for *any* direction and is asserted to reproduce all six
exactly, then reused to derive all 12 edge and 8 corner snap orientations
(normalised sums of 2 and 3 adjacent face directions) — one function instead
of a hand-solved table. Clicking a face/edge/corner (without much drag) still
calls `CameraState.set_orientation`; a drag past a small pixel threshold
orbits via `CameraState.orbit`, exactly like the axis-ball design but now a
real threshold rather than two disjoint hit-test regions (ball vs disc). The
widget is now also draggable to a different screen corner (a grip strip,
title-bar style, persisted the same way a `GuiWindow`'s position is). Not
ported, same as before: the eased snap animation.

**Refinement against three reference screenshots (2026-08-13, later
still).** The ViewCube above, checked against three Autodesk/SolidWorks-style
references, closed four gaps: the axis triad went from a small corner accent
to a long, bold pair of lines (`_AXIS_LINE_WIDTH`/`_AXIS_OVERSHOOT`, both
larger, plus a 1px dark halo behind each label so a same-hue letter over a
similar-hue backdrop stays legible); the cube gained its own small, fixed
perspective (`_project`, a weak-perspective scale keyed to each vertex's
depth, independent of the main viewport's projection); and the previously
unported zoom/pan corner buttons are now a home icon, a pair of 90°-roll
arrows and edge nudge-triangles (`emtk.gizmo.draw_chrome`/`hit_test_chrome`),
wired to `CameraState.turn`/`MolView.reset_view`. A fourth reference element,
a bottom-right dropdown, is drawn and hit-tested but deliberately inert — its
actual menu contents were not identifiable from the reference crops, so it is
a placeholder rather than an invented submenu. Per-face perspective-slanted
label text (the one reference detail *not* attempted) needs a `Painter.text`
rotation parameter that does not exist and was judged out of scope for a
gizmo refinement — see [chimol-emtk.md](../plugins/chimol-emtk.md)'s dated
entry for the full account, including the numerically-verified turn-axis
sign conventions and why there is no "nudge-up" button.

**Phase 4 removed (2026-08-13, later still).** User: *"gizmo is ugly as fuck
remove."* Removed outright rather than kept disabled behind a flag —
`emtk/gizmo.py` deleted, every wiring point in `internal_gui.py`
(`Hit.kind == "gizmo"`, the `_gizmo_*` state fields and methods, the
mouse_press/drag/release/is_dragging/hover-tooltip branches, the
`layout_info` footprint reservation, the final `_paint_gizmo(p)` call),
`canvas_base.py`'s three `on_gizmo_*` callback assignments and `view.py`'s
`on_gizmo_home` wiring, `emtk/__init__.py`'s gizmo exports, `test_gizmo.py`
and `gizmo_baseline.py` (and its rendered PNGs) all removed. Three rounds of
work across this session (the axis-ball port, the ViewCube redesign, the
chrome refinement) went into this before the removal — recorded above and in
[chimol-emtk.md](../plugins/chimol-emtk.md) as an honest account of what was
tried, not scrubbed from the log. `AXIS_ORIENTATIONS`/`_orientation_for_direction`'s
generalised orientation-solving math (any direction → `(elevation, azimuth)`,
not just the 6 axis-aligned cases) does not currently exist anywhere else in
the tree; if a future session wants a different view-navigation aid, that
derivation is worth re-reading from git history rather than re-deriving.
Definition-of-done Phase 4 below is unchecked again; the phase is closed as
**not shipping**, not as still open.

## Widget merge (2026-08-13, later the same session)

User: *"all chimol widgets and autoform must be in emtk."* Scoped by a
clarifying question first, because a literal reading (move the AutoForm
*package* into chimol) would have inverted the dependency graph of a
chisurf-wide, 170-file, 75-plugin-directory framework that predates chimol.
Confirmed scope: `renderer/ui/` (the original nineteen-plus-widget port)
merges into `emtk/` so chimol has one widget namespace, and
AutoForm's one narrow bridge (`qt_host.py`, used by exactly two custom
sections, `code_editor_section.py`/`memory_editor_section.py`) is repointed
at the merged package. AutoForm's own package stays at `chisurf/gui/autoform/`,
untouched, its 170 call sites unaffected.

Mechanical but real: 69 files' imports fixed across the chimol plugin, 5
outside it, plus build tooling (`bake_chrome_atlas.py`'s `OUT_DIR`,
`port_imgui_widget.py`'s scaffolder target), two guard tests
(`test_chrome_atlas.py`'s module scan, `test_qt_seam.py`'s allowlist —
which also surfaced two pre-existing gaps unrelated to the rename:
`emtk/qt_host.py` and `cmd/inspect.py` both import Qt in a guarded,
function-local way that had never been added to the allowlist), and docs.
Full account in [chimol-emtk.md](../plugins/chimol-emtk.md).
