# GopichSzabo stops rebuilding

# Why

Phase-5 row, and the purest example of the crossing rule: the arithmetic
is already engine-side, but the *object* is rebuilt per likelihood
evaluation — construction cost and a numpy eigendecomposition guard paid
once per iteration of a scipy loop. Wrapping that loop in C++ would be
the measured 0.99× regression; the fix is persistence plus moving the
loop's owner.

# The job

1. Persist the engine object across likelihood evaluations; rebuild only
   when the *scheme structure* changes (rate values are updates, not
   rebuilds — the `assign_pda_histogram_function` cache keyed on what
   actually invalidates is the template).
2. Delete the redundant eigendecomposition guard — but first find what it
   was guarding (a silent `try/except` around a degenerate scheme?) and
   keep the *refusal*, loud, if the case is real.
3. Move `fit()` onto `bff.Minimizer` via the existing objective surface;
   likelihood objective, so `objective_type` must say so (the BUG-10
   likelihood-ratio threshold work is the precedent).
4. Measure per-evaluation cost before/after; the rebuild is the number to
   report.

# Definition of done

- [x] Zero engine constructions inside the likelihood loop (counted, the
      way the zero-update_model pins count). `EngineCache` persists one
      `tttrlib.GopichSzabo()` per `(n_states, n_colors)`; a real `fit()`
      call making 139 likelihood evaluations makes 1 construction, counted
      independently of the module's own bookkeeping in
      `test_the_fit_builds_the_engine_once_across_the_scipy_loop`
      (`test/fluorescence/test_gopich_szabo.py`).
- [x] Fit answers unchanged on the reference dataset; timing reported. See
      "Measured" below; `test_persisting_the_engine_gives_identical_likelihoods_to_rebuilding`
      pins persisted-vs-rebuilt agreement to 1e-12, and
      `test_the_persisted_fit_recovers_the_same_answer_as_before_persistence`
      reruns the pre-existing recovery fixture through the now-default
      persisted path.
- [x] The guard's real case (if any) refuses loudly instead of silently

      and only two are true yet.

# Measured

Persistence and the guard trim are done; **`fit()` is not on `bff.Minimizer`**
(see "What did not land"), so scipy's `Nelder-Mead`/`L-BFGS-B` still own the
loop — persistence just stops it paying for a C++ object and a numpy
eigendecomposition it was throwing away every evaluation.

- **Construction count**, the number the job asked to report: a real fit
  (`n_states=2`, 300 bursts of ~50 photons, the module's own recovery
  fixture) makes 139 likelihood evaluations and, before this change, 139
  `tttrlib.GopichSzabo()` constructions plus 139 discarded Python
  eigendecompositions. After: 1 construction, measured by wrapping
  `tttrlib.GopichSzabo` to count independently of `EngineCache`'s own
  counter (both agree).
- **Wall time**: modest and noisy on shared hardware — min-of-5,
  interleaved, 300 evaluations of a 4-state scheme (bigger than the 2-state
  fit above, to make the guard's cost visible against the C++ call's own
  cost): 612 ms rebuilding every call vs 544 ms persisted, **~1.13x**. On
  the 2-state case the two are within measurement noise of each other
  (single runs ranged 458-1350 ms either way on this box, which several
  sibling agents share). The honest reading: for the small state counts
  Gopich-Szabo schemes actually use, the per-photon C++ likelihood itself
  dominates, not the guard or the construction — the *count* (139 → 1) is
  the robust claim; the wall-clock win is real but small, the same pattern
  `chisurf/core/fitting/minimizer.py` records for its FRET graph ("the
  crossing was never the cost here").
- **Fit answers**: `rate_matrix_from_rates` recovered `[2928, 1025]`
  against a simulated truth of `[3000, 1000]` (within the existing
  fixture's `rel=0.15` tolerance, unchanged from before persistence);
  persisted-vs-rebuilt-every-call log-likelihoods agree to `1e-12` across
  four rate/efficiency combinations including revisiting a structure with
  new values.

# What did not land: `fit()` on `bff.Minimizer`

Blocked, not skipped. `IMP.bff.Minimizer` is MINPACK `lmdif`: a
least-squares optimiser over a **residual vector**, and it refuses outright
when there are fewer residuals than free parameters —
verified directly: `Minimizer: 2 parameters against 1 residuals; a
least-squares fit needs at least as many residuals as parameters`. The
`PDA3c`/BUG-10 precedent this job item points to works because that model's
`objective_type = "likelihood"` residuals are **per-burst** deviances
(`r_j = sqrt(2(l_sat_j - l_j))`), so `sum r_j^2 = const - 2 logL` is a
proper least-squares problem with as many residuals as bursts.

`tttrlib.GopichSzabo.log_likelihood(times, colors, offsets)` returns one
**total** scalar over all bursts in a single batched C++ call — that
batching is the point, and the source of most of this module's speed. There
is no way to get the per-burst decomposition PDA3c's residual trick needs
without either (a) tttrlib exposing a per-burst log-likelihood array (a
real engine change, out of this PRD's footprint of `gopich_szabo.py` +
tests), or (b) calling the engine once per burst from Python, which
re-introduces exactly the chatty per-item C++ crossing Phase 5 exists to
remove — a regression, not the fix. A single scalar residual
(`sqrt(-2 logL)`, `m=1`) was tried and confirmed refused by the `m >= n`
check above for any fit with more than one free parameter, which is every
real Gopich-Szabo fit.

**Where to pick this up**: file a tttrlib request for
`GopichSzabo.per_burst_log_likelihood(times, colors, offsets) -> ndarray`
(same signature, one value per burst instead of the sum) — mirroring how
`ChiSquared` already exposes both a scalar and a residual vector. With that,
`fit()` can build `PDA3c`-style deviance residuals
(`r_j = sqrt(2*(logL_j.max_possible - logL_j))`, or, more simply, treat the
per-burst log-likelihoods directly as a likelihood-ratio-style residual
against a saturated reference) and route through `bff.Minimizer` exactly as
the job item describes. Until then `fit()` stays on `scipy.optimize.minimize`,
now over the persisted engine.
