# PRD-137: imp.bff as an independent core, with a connection layer to IMP

**Status**: implemented (2026-09-08); release mechanics open. **Done**: steps 1–3; PRD-138 (consolidation +
interface pass); step 4 -- the connection layer is `src/imp/` reached through
one flat `src/ImpLayer.cpp` (IMP's tooling compiles only `src/*.cpp` and
`src/internal/*.cpp`, and links only `include/*.h` + `include/internal/*.h`,
so headers stay flat and are named in `src/imp/Headers.cmake`); step 5, the
main cut -- `get_av` computes the accessible volume without an `IMP::Model`
(`OccupancyGrid` is the core raster, `AVOccupancyMap` the layer's particle
view; `get_av_lattice` is the decorator's lattice path over spheres), the
restraint factories left `Scoring.h` for `Potentials.h`, and no core file
includes a layer header. All local on `independent-core`, not pushed.
The em cut is done (the core writes MRC2014 itself; `EmBridge.h` is the
layer's em door). Step 6a–6c done (2026-09-08): `standalone/include/` shims
the `IMP::Object`/`IMP::algebra`/`IMP::Pointer` vocabulary, `standalone/`
builds `libimp_bff` and the Python module with no IMP, `import IMP.bff`
works with no IMP loaded, and the one test suite runs as two lanes
(`test/conftest.py`: standalone 718/0, IMP build 1790/0). The exception
family is `IMP.bff.ValueException` etc. in both builds.
Step 6d (2026-09-08), owner's naming: package **`bff`** is the core (PyPI
wheels from the root `pyproject.toml`, scikit-build-core over `standalone/`;
conda from `conda-recipe/recipe-core.yaml`), package **`imp.bff`** stays the
IMP module build; both import as `IMP.bff` and are alternatives (each
recipe constrains the other; `IMP.bff.get_build()` says which is present).
`rotamer_library/` + `cgprobe/` (62 MB) left git: `data/registry.json`
(sha256) is tracked, the files are served from
`https://www.peulen.xyz/downloads/imp.bff/` (uploaded 2026-09-08),
`utility/data_registry.py --fetch` restores a checkout, CI caches the
download keyed by the registry (tttrlib's pattern), conda builds fetch
before packaging, and both builds fetch a file on first use. Gated locally: the wheel
built, installed into a venv with no IMP, imported, served its shipped data
and fetched registry files from a local server with sums checked; standalone
lane 724/0; IMP build 1794/0. **Owner's step**: on pypi.org register the project `bff` with this repo's
workflow as trusted publisher.
**Unverified until CI runs**: the cibuildwheel jobs (the manylinux/macOS
images build RMF via `utility/wheel_deps.sh`); Windows wheels deferred.
PRD-137 is implemented end to end; what remains is release mechanics.

**Where the line falls for dye simulation** (owner, 2026-09-08): the core
covers rotamer-library dyes, grid diffusion, RRT linker sampling, probe
force fields and FASPR packing. Attaching a dye onto a hierarchy
(`attach_probes`, `place_probe`) and Langevin dynamics on the attached dye
(`make_langevin_simulator`, `AttachedProbeDynamics`) **stay IMP-only** --
they are built on IMP's integrators and decorators. The owner ruled that
road stays IMP-only rather than porting an integrator (2026-09-08).

What a port would actually need, measured 2026-09-08, should anyone revisit
it: the **topology** is already core (`ProbeForceFieldSystem`,
`create_forcefield_system`, `TopologyBuild.cpp`, `ForceFieldCIF.cpp` -- bonds,
angles, torsions, LJ types). The **energies** are array-based and IMP-free in
their signatures although they sit in the layer's `Potentials.h`
(`clash_energy`, `go_energy`, `lennard_jones_bead_energy`,
`generalized_born_energy`, `ramachandran_energy`, `residue_asa`, all over
`const std::vector<double>& xyz`), so they would move the way `States.h` was
split out. What does **not** exist anywhere in bff is **gradients**: IMP's
restraints supply the derivatives its integrator steps on, and nothing in the
core differentiates the force field. A core Langevin is therefore
analytic gradients for the bonded, LJ and soft-sphere terms plus the
integrator itself, validated against the IMP road -- bounded, but real work,
and more than the "attachment plumbing" it looks like from the outside.

What is *not* available is a single library that is half shimmed and half
IMP-linked: the shim tree and IMP's headers redefine the same classes
(`IMP::Exception`, `IMP::Object`, `IMP::Pointer`, `IMP::algebra::VectorD`),
so no translation unit holds both (measured). Building the *same sources*
against real IMP with no shims does work -- the headers compile and 83 of
84 sources compiled in a hand-rolled IMP-mode build, the one failure being
a logging-macro flag rather than a design problem -- which is what
["using IMP as a library"](https://integrativemodeling.org/2.25.0/doc/manual/uselibrary.html)
describes: `find_package(IMP)`, `IMP_INCLUDE_DIR`, `IMP_<module>_LIBRARY`,
no IMP build tooling. That is a second *configuration* of these sources,
not a way to drop the shims: the shims are what lets the core build with no
IMP present, which is the whole point of the pip package. See PRD-139 for
whether the IMP-mode build should move off IMP's in-tree tooling onto this
project's own CMake. `IMP.bff.labellib` is the core's
LabelLib-compatible face (same names, same signatures), so bff replaces
LabelLib for callers who only want volumes.

## Why (owner, 2026-09-07)

IMP is hard to install and slow to release, and there are environments where
it is neither installable nor needed — chisurf fits fluorescence data with bff
and needs no IMP. Measured: chisurf uses 38 `IMP.bff` symbols; 36 need no IMP.
**This is not a replacement for IMP**: IMP integration stays, as an explicit
connection layer, so bff functionality remains usable inside IMP.

## Decisions

| | |
|---|---|
| Scope | Standalone retains all functionality. |
| Shape | IMP-free core + connection layer (`src/imp/` sources behind the flat bridge `src/ImpLayer.cpp`; headers flat, listed in `src/imp/Headers.cmake` -- IMP's tooling allows no public include subdirectory; IMP concepts: restraints, decorators, optimizer states, MD). |
| `IMP::em` | Removed — `DensityGrid` replaces `SampledDensityMap` under `PathMap` (done). |
| `IMP.rmf` | Removed from the code — RMF's own API (done); RMF itself kept, avro backend, HDF5 goes. |
| Parameter store | bff owns it (`Port`/`FactorGraph`); the layer exposes scalar fit variables as `isd::Nuisance`-style particles, synced on state updates. |
| Import name | `IMP.bff` in both builds. Packages: `imp.bff` (core, PyPI+conda) and `imp.bff-imp` (layer, conda). |
| Layout | Flat, IMP-compatible (PRD-138). |

## Deferred, with the reason recorded in the code

- **Which radii a structure's obstacles get.** The Labelizer's site volumes
  are built through an AV door (`ll_set_av_door`): the core's road assigns
  radii from bff's van der Waals table, IMP's road (installed by the layer)
  from IMP's force field. The two builds therefore score AV-mode Labelizer
  sites differently until the owner picks one table. `ll_get_av_door_name()`
  says which is in force.

Dropping `rmf` from `dependencies.py` works out-of-tree but silently disables
`IMP.bff` in-tree: without the module edge bff sorts before the configure step
that writes `build_info/RMF`. Lands with the standalone build.

## 2026-09-07 -- what changed for chisurf in imp.bff's interface pass (PRD-138)

- `IMP.bff.compute_av` is `IMP.bff.get_av` (19 renames, no aliases). Patched
  in this checkout, uncommitted: `chisurf/core/structure/av/__init__.py`
  (imports `get_av as compute_av`, so chisurf's own name is unchanged) and
  `test/benchmarks/benchmark_quenching_posterior.py`.
- Every `std::vector<double>` bff returns is now a float64 ndarray (owning its
  buffer), not a tuple of floats. Code that relied on tuple semantics --
  truth-testing an empty result, `+` concatenation, `list.index` -- needs
  `len(x) == 0` / `np.concatenate` / `np.where`.

## Where to pick this up — can chisurf drop `imp` for the `bff` wheel?

**Measured 2026-09-09** against a freshly built IMP-free core (`standalone/`
configured with `IMPBFF_PYTHON=ON`, `IMPBFF_WITH_RMF=OFF`;
`IMP.bff.get_build() == "core"`, imported with the real IMP stripped from
`sys.path`).

**Answer: not yet, but the gap is four call sites, and none of them is a bff
gap.** Every one of the **70 `IMP.bff` names chisurf imports is present in the
core** — nothing chisurf asks bff for lives in the connection layer. The
surface diff is 1275 public names in the IMP module build against 913 in the
core; the 362 extra are IMP's own config constants plus the layer (docking,
FPS project I/O, probe attachment and Langevin, the restraints, the
hierarchy/em/algebra bridges, the force-field energies), and chisurf calls
none of them. Functional check: `get_av` over `(N, 4)` arrays from the core's
own `read_pdb_records` reproduces an AV for hGBP1 residue 18 CB (ng 29, 5515
occupied voxels) with no IMP loaded.

What still needs IMP itself, in the order it should be done:

1. **`chisurf/core/fio/structure/coordinates.py` is the blocker** — it does
   `import IMP, IMP.core, IMP.atom` at module level, so `Structure(pdb)` and
   `read_coordinates(...)` fail without IMP even though *the import chain
   itself* is fine (measured: every other `chisurf.core` module imports clean
   against the core). Two things the core cannot yet replace:
   - **CHARMM radii.** `radii="charmm"` is the default and is what the AV
     simulation sizes probes with. The core's `read_pdb_records` /
     `load_structure_with_vdw` give the *element's van der Waals* radius
     instead. This is the same open question PRD-137 already records as
     deferred ("which radii a structure's obstacles get"); it has to be
     settled here, not worked around. `radii="vdw"` already runs on the core
     (9315 atoms, no IMP).
   - **mmCIF.** `read_coordinates` reaches `IMP.atom.read_mmcif` for `.cif`.
     The core refuses one: `load_structure` answers "No molecule read from
     file" and `read_pdb_records` "No ATOM/HETATM coordinates found", on a
     plain *and* on a gzipped `.cif`. bff's other `.cif` doors
     (`read_forcefield_cif`, `read_component_template_cif`) are force-field
     and template CIF, not atomic coordinates. **The trap**: the core's error
     is a `ValueException` about content, not about format, so a caller that
     catches broadly reads it as a bad file rather than as an unsupported one.
2. **`chisurf/core/models/structure/rmf.py`** — RMF writing through
   `IMP.rmf`, already behind a `try`/`except` that raises `RmfWriterError`.
   Note the wheel has **no RMF at all** (PRD-139: librmf drags Boost.Iostreams
   and all of ICU, 40 MB), so this degrades on the wheel even if IMP goes; the
   core conda package keeps RMF.
3. **`chisurf/plugins/modelling/fps_json_editor/core/mrc.py`** — writes an MRC
   map through `IMP.em.create_density_map` + `write_map`, voxel by voxel. The
   core writes MRC2014 itself (`DensityGrid.write_mrc`), so this is a direct
   port and the cheapest of the four.
4. **`chisurf/plugins/modelling/fret/`** — the docking engine is IMP.pmi, and
   the workflow needs layer-only bff (`dock_minimize`, `refine_docking`,
   `screen_structures`, `write_fps_project`, `olga_vdw_*`). This plugin is the
   reason `imp` is declared mandatory, and it is the one part that genuinely
   stays IMP-only.

**Found on the way, and it blocks (4) before any of this matters**: the FRET
plugin is **already dead in this environment**, independent of the pip
question. imp.bff deleted every Python subpackage on 2026-08-23
(`6584e80`, "delete pyext/src: zero .py files in pyext, flat IMP.bff namespace
only"), and nine files under `chisurf/plugins/modelling/fret/core/` still
forward to `IMP.bff.fret.*`. Every one raises `ModuleNotFoundError: No module
named 'IMP.bff.fret'` on both builds — the IMP module build here and the core
alike. [known-issues](../references/known-issues.md) already carries this as
the open `test_plugin_entrypoints_import[fret]` entry; what this measurement
adds is **when and why** the subpackages went (`6584e80`, the flat-namespace
cut) and that **no build restores them** — the choice is not "install the
Python portion", it is de-forwarding `fret/core` onto the flat surface.

**So the shape of the decision**: `imp >= 2.25` can move from a *mandatory*
dependency to an *optional* one behind the FRET docking plugin once (1) is
resolved, which is one radii ruling plus an mmCIF reader. Dropping it outright
also drops FRET docking, RMF output and mmCIF reading.
