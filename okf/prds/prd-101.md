# ChiMOL's interface lives in the viewport

# Where to pick this up

**Handover, 2026-08-11.** Direction stated by tpeulen: *"all should live in
opengl/viewport, so that app can work in pyqt and web the same way, by all i
mean all relevant interfaces, incl menu(s)"*, styled after **Dear ImGui**
(`junk/imgui`, vendored, annotated) with **in-view draggable windows**, and
*"in ray or png saves they should of course not appear"*.

**Landed:** the window frame (requirement 1). **Next:** requirement 2, the
density controls — which is also where the "super slow / gets stuck when
playing with thresholds" report has to be fixed, because the port is the moment
the recompute path is rewritten anyway.

The concept that tracks day-to-day state is
[chimol-viewport-ui](../plugins/chimol-viewport-ui.md); this PRD is the design
and the full list, so nothing here depends on remembering a chat.

## Why this is a port and not a rewrite

`InternalGui` is **already** a toolkit-free layout and hit-test engine. It
paints through six operations (`chimol/cmtk/painter.py`) and rasterises
as GPU quads (`ui/quad_painter.py`); the object list, sequence strip,
mouse-mode block, wizard panel, pop-up menus, the command prompt and — since
2026-08-11 — the system-info panel are all drawn that way. Qt is one
implementation of the painter, not the substrate.

So "move the UI into the viewport" is: give each remaining panel a body that
draws through `Painter`, and delete the dock. The only genuinely new mechanism
was a **window** to put them in.

**What was deliberately not taken from ImGui:** its immediate-mode core — the
ID stack, the `Begin`/`End` protocol, its draw list and font atlas. chimol's
chrome is *retained*: panels persist between frames and hit-test themselves.
Adopting IM would mean rewriting every existing panel to gain nothing the quad
painter already does, and a second glyph atlas is exactly the duplication the
painter seam exists to prevent. What was taken is the **look** and the **window
interactions**, read from the source and recorded in the file headers.

## Requirements

### 1. An in-viewport window frame — **DONE 2026-08-11**

`GuiWindow` in `internal_gui.py`, with `add_window` / `window` /
`raise_window` / `remove_window`, `layout_windows`, `_window_hit`,
`_press_window`, `_drag_window`, `_paint_windows`.

Title bar, move, corner resize, collapse (button *and* title-bar double-click),
close, raise-on-click, clamped inside the viewport. Contents arrive through a
`body(painter, rect)` callback so the frame knows nothing about what goes in
it — that callback is the seam requirements 2–5 hang off. `lines` covers the
plain-text case.

Behaviour is ImGui's, from its source rather than memory: 32×32 floor
(`WindowMinSize`), 1 px border, **4 px grab reach outside** the resize corner
(`WindowBorderHoverPadding` — a one-pixel edge is not a mouse target), grip
≈1.1 line-heights, fold on title-bar double-click, and the `StyleColorsDark`
palette.

Two decisions worth not re-deriving: windows are **clamped inside the
viewport**, because there is no window manager underneath to retrieve one
dragged off the edge; and `draw_windows = False` removes them from a frame —
`png` wraps its framebuffer grab in `_windows_hidden`, while `ray` renders
through the tracer and never saw chrome at all.

12 tests, every decoration hit-tested (`test_viewport_windows.py`).

### 2. Density / contour controls into a window — **panel DONE 2026-08-11**,
dock removal outstanding

`renderer/density_window.py`: the map's name and range, the three mode buttons,
and the value histogram with a marker standing at each contour — drawn through
the six painter operations, so it runs on the desktop and in the browser from
one implementation. Wired to the **same `VolumeViewModel`** the dock used;
nothing about that model was Qt-specific.

**The drag no longer re-contours.** Measured: a 20-step drag causes **0**
rebuilds and the release causes exactly **1**, where the dock ran marching
cubes over the whole grid on every value change — which is the whole of the
"slow and gets stuck" report. Same trade the sequence strip already makes.

**The three modes exist and differ.** `surface` → mesh geometry, `mesh` →
**line** geometry, `voxel` → points. Two of the recorded defects close with it:
`mesh` looked identical to `surface` because nothing ever asked for the
wireframe branch that was already there, and `voxel` did not exist. Voxels are
sub-sampled to the `dots.max_points` budget **evenly through the array, not the
first N**, so the cloud keeps the shape of the density rather than its corner.

The mode is read off the levels' own `style` rather than kept beside them: a
second field naming the same thing is two values that must agree and eventually
will not.

**On screen since 2026-08-11:** `density_panel [toggle|on|off]`, and
**Display ▸ Density controls** in the viewport menu bar. The Qt Map dock is
still built; deleting it is what is left of this requirement.

**The input seam this needed, and every other panel will:** `GuiWindow` gained
`on_press` / `on_drag` / `on_release`, the counterpart to `body`. A press that
returns true starts a body drag and consumes the event — which is what stops a
drag inside a window also rotating the molecule behind it — and `on_release` is
where a panel that batched work during the drag does it. *Trap already hit:*
`InternalGui.drag()` guards on which drag is in progress, and adding a third
kind means adding it to that guard too; without it the router was never
reached and the marker silently would not move.

### 2-bis. Folding the fixed docks — **BUILT AND REMOVED, 2026-08-11**

Asked for, then withdrawn the same day: *"do not allow to fold, difficult to
unfold"*. The mechanism worked — the docks collapsed and the scene grew from 598
to 806 px — and the mechanism was not the problem. **A folded dock leaves only
a chevron, and a 14-pixel chevron at the edge of a dark viewport is not a target
anyone finds**, so folding was a one-way door in practice.

Recorded rather than deleted quietly, because the *idea* will come back the
moment someone wants the molecule bigger on a small screen. What it needs, if it
does: the folded state must leave something with a **readable label** — a title
strip along the edge, not an arrow — or the whole dock must be hidden and
restored from a menu that is always there (`set seq_view, off` already works
that way).

Two things from that work were kept because they were right independently: the
short-viewport regression it exposed (the object rows fall into the mouse-mode
block, which is hit-tested first, so the A/S/H/L/C buttons stop opening — a
**pre-existing** defect recorded in `okf/reviews/findings.md`) and
`effective_column_width()`, which is now the single place the column's width is
reserved.

### 5-ter. The toolbar, the context menu, `help`, and measurements as objects —
**DONE 2026-08-11**

* **Toolbar in the viewport**, migrated from `controls_panel.py`. Every button
  is a **command**, which is the difference: the Qt buttons were wired to Qt
  slots, so the row worked only on the desktop and taught nobody the command
  behind it. Two commands had to exist for that — `toggle_rep` (a button that
  only ever *shows* is a button you press once) and `info_panel`.
* **`config` is a real command.** `__config__` was a sentinel the Qt menu
  builder intercepted, so the moment anything else sent it — the viewport
  toolbar, a typed line, a script — it answered *"Command '__config__' is not
  implemented"*. A sentinel only one caller understands is not a command.
* **`open` with no path opens the dialog**, which is what File ▸ Open and the
  toolbar send; it used to answer with a usage line.
* **Right-click in the scene opens the object menus.** The mouse-mode block has
  always promised this — its `SnglClk` row reads `R  Menu` — while the five
  menus were reachable only from the object list's buttons.
* **`help` answers in the info panel**, which scrolls, takes the full band and
  widens to 78 columns once the answer is longer than eight lines. It went to
  the prompt's feedback line, which shows **one line**, so a hundred-name
  command list scrolled straight past and `help` was in practice unreadable.
* **Measurements are objects.** A `distance` gets a row under `sele` with its
  value, and clicking the row switches it off — *off*, not deleted, which is
  the whole point of an object having a switch. `measurement <name>,
  on|off|toggle|delete` is the command behind it. They were drawn into the
  scene and listed nowhere, so one could only ever be removed, and only by
  knowing the name it was given.

### 3. Hierarchy into a window — **DONE 2026-08-11**

`renderer/hierarchy_window.py`: the tree with a disclosure arrow and a switch
per node, reading the **same `HierarchyNode` tree** the Qt dock reads rather
than a copy. `hierarchy_panel [toggle|on|off]`, plus **Display ▸ Hierarchy**
and a **Tree** toolbar button.

Switching a node off takes its **subtree** with it — what the Qt panel's
tri-state check boxes expressed — and what reaches the viewer is the set of
coordinate rows those nodes cover, through the same `_apply_hidden_rows` the
dock used.

**The search box is there too.** It was left out at first as "a keyboard-focus
problem of its own" — it is one, and the answer was to generalise the solution
the chrome already had for the prompt rather than to do without.
`cmtk/text_field.py` holds a string and a caret and nothing else (no
history, no log, no submit — that is what makes it *not* the prompt), and
`InternalGui.focused_field` owns **which** field has the caret, because a key
arrives at the panel and something has to say where it goes. Taking focus takes
it *from* the prompt: two carets on screen is two places a keystroke could be
going with no way to tell which.

Filtering rules, both from the Qt panel's proxy model and both worth keeping:
a node shows if it **or any descendant** matches (a hit three levels down is
unreachable if its ancestors are filtered away), and **everything under a match
shows** (a chain with its residues filtered out is not the chain). A filter also
opens the tree — re-folding by hand is the opposite of searching. Escape and a
click on a row give the keyboard back, or every shortcut is swallowed by a box
nobody is looking at.

**Three defects reported against the first cut, all fixed 2026-08-11:**

*No scroll bar.* `_draw_scrollbar` draws a track and a thumb whenever the tree
is taller than the window, and the thumb is **draggable** — a bar that only
reports is missing, and the wheel is not discoverable.

*"Filter does not work."* Literally true, and not in the filter: `draw` looked
the tree up **first** and returned the sentence *"No hierarchy"* before the
search box was laid out. A PDB carries no `rmf_hierarchy`, so for every
ordinary structure there was nothing on screen to type into. Two changes: the
field is drawn before the tree is looked up, and a structure without an RMF tree
gets one **synthesised from its atom table** — object → chain → residue, which
is the tree PyMOL's own panel shows. The root carries the object's *display*
name, not its internal id: the object list says `1rtd` and a tree rooted at
`obj2` reads as a different structure.

*"Builds slow for large NPC."* Two costs, and the second was the real one:

| | before | after |
|---|---|---|
| first flatten, 500 chains × 400 residues | 327 ms | 0.17 ms |
| flatten on a repaint | 327 ms | 0.0005 ms |

The walk over every node ran in `draw`, so it was paid **on every repaint** —
the camera stuttered while it moved. It is cached now on
`(tree, needle, collapsed, expanded)`, which is everything that changes it. But
caching alone still leaves a 327 ms first frame, because the tree started
**fully expanded**: 200 501 rows for a window that shows twelve. So the default
is depth-based — `_OPEN_DEPTH = 1`, the object and its chains — with explicit
`_collapsed` and `_expanded` sets over the top. Two sets rather than one,
because "shut unless opened" and "open unless shut" are both needed, at
different depths.

`_matches` also became iterative: a residue-level tree is deep enough to hit
Python's recursion limit, and a `RecursionError` inside a paint is a filter that
"does not work" with nothing said about why.

### 4. The 3-D view **is** the window — **DONE 2026-08-11**

Stated by tpeulen: *"no toolbar needed anymore, no chisurf dock needed anymore
just make 3d view the main widget in window. no other widgets, no chimoldocks,
no toolbar."*

`setCentralWidget(self.viewer)` and no `DockArea` at all. Gone with it:

- the **Qt hierarchy dock** — the tree is in the viewport, and two trees over
  one model is two things that can disagree;
- the **toolbar**, `setParent(None)` rather than `hide()`: a `QToolBar` whose
  parent is a `QMainWindow` is shown again by Qt's own layout the moment the
  window is, so hiding it left it on screen. The object stays alive through
  `self.controls` because a few call sites still read `button_info.isChecked()`;
- the **Qt menu bar**, which was drawing a *second* copy of the viewport's menus
  directly above them — visible in the first grab of the new layout, and the
  reason to look at the picture rather than the assertions.

`_build_view_menu` and `_install_menu_bar` are kept for a host that wants a
native bar; nothing calls them.

### 4-ante. The Command and Objects docks are gone; the prompt completes —
**DONE 2026-08-11**

`CommandLine.complete()` had been written all along with **nothing calling it**:
`key()` did not handle Tab, and Tab would not have arrived anyway — Qt resolves
it in `QWidget.event` and moves the focus before any key handler sees it. Three
gaps, one of which (the completer itself, from the same dispatcher the console
used) was already wired. The widget now claims Tab **only while something is
being typed**; otherwise it still moves the focus, which is what it is for.

Both docks are **deleted rather than ported**: the object list has been in the
viewport's panel column all along and the prompt *is* the command line. Two
views of one thing that can disagree is worse than one, and only one of them
exists in a browser.

### 4-bis. A structure with hundreds of chains — **FIXED 2026-08-11**

The NPC (`pdbdev_00000012`, 234 184 atoms) filled the whole window with one
sequence row per chain and left no molecule.

**The row-per-chain split was wrong, and PyMOL says so.** Checked in
`Seeker.cpp`: `nRow++` closes the **per-object** loop, so PyMOL builds one row
per object and shows chains *inside* it — `seq_view_format 3` writes the chain
id as its own column at each boundary. Transcribed rather than approximated
this time. A row per chain reads fine on a four-chain protein and is unusable
on an integrative model, which is the case that found it.

The chain markers are columns that name **no residue**, so their
`residue_indices` entry is **-1** and everything downstream drops negatives —
without that, clicking a chain label selects whatever residue happens to share
its column index.

### 4-ter. Selection was slow, and it was the map — **FIXED 2026-08-11**

`_atom_residue_indices` (added for the cross-chain fix) is O(n log n) over
*every atom* and was recomputed on **every** selection refresh and every pick.
Cached per object in a state field, cleared where the residue table is written.
Measured on 1RTD (17 784 atoms): **18.33 ms → 0.0007 ms**, and a selection
marker refresh is now 0.22 ms. On the NPC the first build is ~250 ms and every
one after it is free.

### 5. The menu bar in the viewport — **DONE 2026-08-11**

Asked directly — *"where are my menus in the 3d view?"* — and the answer was
that they were a **Qt** menu bar, which on macOS Qt takes away to the *system*
bar at the top of the screen, nowhere near the viewport, and which in a browser
does not exist at all.

`InternalGui.menubar` now holds the `(title, entries)` pairs and
`layout_menubar` / `_menubar_hit` / `open_menubar` / `_paint_menubar` draw and
drive them. The entries are the ones `object_menus.py` already fed to the
in-view A/S/H/L/C pop-ups, so only the *bar* was new. Click a title to open,
click it again to put it away, and **slide along the bar to switch** — the
behaviour every menu bar has and which, without it, forces a click per title.

The panel deliberately does **not** know which menus an application has: the
host fills `menubar` (the window does it in `sync_internal_gui` from
`MENU_BAR`), and with nothing supplied there is no bar and no band taken.

`top_band_height()` is new and is what the renderer must ask for: the bar and
the sequence strip **stack**, and asking for the strip alone drew the molecule
under the bar.

The Qt bar is still built as well, which on macOS is a reasonable place for it
to also appear; deleting it is a separate decision from having the menus in the
view.

### 6. The browser chrome must not scale with the viewport

Reported: in the browser the chrome scales with the canvas and becomes
unreadable when it is small. On the desktop the chrome is laid out in **logical
pixels** and scaled by device-pixel ratio (`_ratio()`); the browser path must do
the same rather than scaling the whole overlay to fit. Chrome is a **constant
apparent size**; the scene takes the rest.

## The rendering defects reported alongside (2026-08-11)

Separable from the UI work. None is diagnosed past a first look; each is
recorded so it is not re-found.

0. **An object called `EMD-3061` broke every menu — FIXED 2026-08-11.**
   Reported as a wall of *"Selection parse error: Unexpected token
   Token(INT, '3061')"*, one per menu click. The name is not chosen by the
   selection grammar — an EMDB entry arrives called `EMD-3061` — and a hyphen
   there is the **range** operator `resi 1-40` needs, so the name lexed as
   `EMD`, `-`, `3061`. Quoting did not help either: there was **no string token
   at all**.

   Fixed in three places, because the name travels three routes: a `QUOTED`
   token that becomes one `IDENT` with the quotes stripped;
   `quote_selection_name`, which the menus now put round any target that is not
   a bare identifier (and leaves `148l` alone, so echoed commands stay
   readable); and `_unquote_name` in the command base, because the commands
   that look an object up **by name** never reach the parser and were matching
   the quotes literally — `zoom "EMD-3061"` said *matched no atoms* about an
   object that was right there.

   Bare `EMD-3061` stays ambiguous with a range **on purpose**. This is the
   punctuation half of a bug the tokenizer already records for `1dg3`, which
   once lexed as INT + IDENT.

1. **Surface representation is broken** — torn shards of triangles rather than a
   closed skin. **Metaball is broken the same way**, which points at the
   Gaussian-splat path they share. User's instruction: **use the next slower
   variant for surfaces** rather than the splat.
2. **Mesh looks identical to surface.** In PyMOL a `mesh` is a *wireframe* of
   the same isosurface — check `RepMesh` before changing anything.
3. **No voxel display mode for density maps** (see requirement 2).
4. **The map panel showed the wrong map — FIXED 2026-08-11.** Reported as
   *"load demo emdb, load other demo, map still in map level adj tool"*.
   `VolumeViewModel._grid` prefers the active object's map and otherwise
   searched `_objects` — which is **insertion-ordered** — *forwards*, so with
   two maps loaded and anything else active it kept editing the **first**. It
   now searches backwards: newest map when nothing map-like is active, and an
   explicitly chosen one still wins. Deleting every map leaves the panel saying
   "No map loaded" rather than describing one that is gone.

   The *scene* half of the same report was checked and is clean:
   `remove_object` drops the object **and** its `<id>:volume_0` scene object
   (`['obj2:volume_0']` → `[]` with a synthetic grid). Tests:
   `test_map_panel_follows_the_map.py`.
5. **`ray` output is too dark** against the live view.
6. **`show as ribbon` does nothing**, and **`trace` duplicates it** — in PyMOL a
   ribbon *is* the backbone trace. Confirm against `RepRibbon`, then remove the
   duplicate entry rather than keeping two names for one thing.
7. **`cell` draws wrongly** — the box is not around the molecule.
8. **Dots do not scale with zoom.** `dots.px_mode` is the flag to check, and it
   is the same "flag read by nothing" shape already recorded for the point
   glyph's half-size defect.
9. **Hidden waters reappear after colouring by atom.** *Not reproduced.
   Photographed, both load paths, 2026-08-11.* The user's recipe is
   `fetch 1f5n` → hide water → select a sidechain → sticks → colour by atom.

   Driven headlessly and **rendered offscreen at every step**
   (`WgpuRenderer.grab_image(chrome=False)` — the wgpu view cannot be grabbed
   with `grabFramebuffer`, which is why counting geometry was tried first and
   is the weaker instrument):

   * **local load** of 1f5n — cartoon → `show nonbonded, solvent` → hide →
     sticks on `sele` → `cnc sele`. The control frame shows the waters
     unmistakably as a spray of white dots; the hidden and coloured frames show
     none, only the pink selection markers.
   * **`fetch 1f5n`** — the real network path, same 411 waters, same result.

   Ten command variants were tried besides
   (`hide everything, solvent` / `… and <object>` / `… and all`, `cnc sele` /
   `cnc <object>` / `cnc all`, `cba`, plain `color`, `set_color_mode` flipped
   and back); every visibility mask is unchanged throughout.

   **What is left is how the steps were performed, not which file was loaded.**
   The remaining candidates are GUI routes that issue something other than what
   was tested: the **`sele` row's** H/S/C menus rather than the object row's,
   and a sidechain selected **by clicking in the viewport** rather than by a
   `select` expression. The cheapest way to settle it is the command log — the
   in-viewport prompt echoes every menu click, so the exact four commands are
   already on the user's screen.

## Performance, filed 2026-08-11 (not fixed, by direction)

* **Density maps are slow.** The isosurface contours the whole grid on every
  rebuild; ChimeraX is the named reference (step/multi-resolution, region
  cropping, caching per level+step, and its `Volume`/`GridData` split).
* **The NPC load has regressed.** Suspects, most likely first and most likely
  *mine*: per-chain sequence rows built in Python inside `sync_internal_gui`;
  `_atom_residue_indices` recomputed O(n log n) over every atom on every
  selection refresh instead of cached per object.

Both in [known-issues](../references/known-issues.md) with what to measure.
**Order:** the migration finishes first, then these — the 3-D view becomes the
main window, and *then* the issues get tackled.

## Reported 2026-08-11 (second batch)

Filed as reported; each is separable.

### A. Orphaned Qt widgets drew over the viewport — **FIXED 2026-08-11**

A little grey `Command line` box sat over the toolbar row (photographed). Cause:
the panels that used to live in the dock area are still **constructed** — a few
call sites read a button's checked state or push text at the console — and a
`QWidget` parented to the window that no layout owns is drawn at **(0, 0),
100 × 30**, on top of the viewport. Four of them were stacked there: `Chinsole`,
`VolumeDock` and two bare containers. `MolViewPluginWindow._detach_orphan_widgets`
cuts the parent link on everything that is not the viewport, the status bar or
the menu bar; the objects stay alive through the attributes that hold them.
`hide()` would not have been enough — Qt's main-window layout re-shows a tool bar
when the window is shown.

The prompt itself is the in-viewport one and is **only drawn when the view is**,
which is what "cmdline must be in window, only show when view enabled" asks for.

### B. `fetch` on top of an existing object — **two defects, one fixed**

Reported as *"fetch structure on top of another break entire geom"* with a
screenshot of `148L` + `2f5n`. It is two independent things, and separating them
took one experiment: **render `2f5n` on its own**.

**B1. Every object was centred on itself — FIXED 2026-08-11.** Scene coordinates
are `(xyz - raw_center) * scale`, and `raw_center` is a `_StateField`, i.e. *per
object*: each `set_structure` computed its own. Measured on the reported pair —
`148L` centred at `(8.4, 45.3, 34.6)`, `2f5n` at `(-11.9, 52.6, 19.2)`, and both
therefore drawn on the origin, interpenetrating. `MolView._adopt_scene_frame`
makes the **first** object define the origin and every later one borrow it, which
is PyMOL's rule; the radius is re-measured about the borrowed centre, because
`_update_view` frames the camera from the largest object radius and a radius
about an abandoned centre clips the object. Single-object behaviour is unchanged.

**B2. `2f5n`'s cartoon has spikes — OPEN, and it is not a multi-object bug.**
Ribbons shoot off to infinity, and they do it with `2f5n` loaded **alone**
(`fetch 2f5n; zoom all`, no other object) — so the multi-object screenshot was
showing this defect plus the superposition above, and fixing B1 does not touch
it. `148L` alone is clean, so the repro is one structure and the difference is
what to look at: `2f5n` is protein **plus DNA** with several chains, and a
cartoon spline that runs across a chain break is exactly this shape. Check the
chain-boundary split in the trace builder (`_build_trace_ups`,
`_residue_chain_ids`) before anything else.

### C. `ray` is too dark — **target restated**

Not "make it brighter": it should come out **close to the live view, just
nicer**. That makes the live view the reference image, so the fix is checkable —
grab both at one camera and compare, rather than judging one picture.

### D. Voxel rendering, ChimeraX-style

The mode exists and is wrong. `MolView._volume_voxel_object` builds
`Geometry(kind="points")` — one screen-space dot per sample above the level, at
a fixed pixel size. tpeulen: *"voxel must be size of grid not hollow points"*.

So a voxel has to be **a cell of the grid**: a box of `grid.step` (in scene
units, i.e. times `_scale_factor`), not a point that keeps its size as the
camera moves. That changes the budget as well as the geometry — the current
cloud is capped at 250 000 points, and 250 000 boxes is three million
triangles.

Read `junk/` before writing anything (tpeulen: *"look in junk how to do!"*) and
annotate the header with what was taken and skipped. Note while reading that
ChimeraX's own "solid" mode is **ray-cast volume rendering with a transfer
function**, not boxes — which is also where the colour and alpha controls below
come from, so the two items are one design.

### D-bis. Colour and alpha controls for density

*"need color ctrl and alpha ctrl for density, check how to do in imgui."* ImGui's
`ColorEdit4` (a swatch that opens a picker) and `SliderFloat` are the reference
for the widgets; `renderer/density_window.py` is where they go, beside the
contour markers and the surface/mesh/voxel buttons. `cmtk/` has no
slider or colour swatch yet — both are new painter-level controls, and both are
reusable, so they belong there rather than inside the density window.

### E. Performance, with the benchmarks named

tpeulen named the two fixtures, which is what makes this measurable rather than
a feeling: **the NPC for scene/load performance**, and **an EMDB map for density
rendering**. Every claim in this section has to cite one of those two.

### F. Selections do not work in the browser

They work in the desktop viewport. Same `InternalGui`, different host — so the
gap is in the web host's event delivery or in the pick path's use of a
desktop-only projection, not in the selection logic.

### H. The info panel scrolled and never said so — **FIXED 2026-08-11**

`help` has put its output in the info panel since the panel learned to hold more
than one line, and `help_setting` did not — it returned 92 setting names to the
prompt's one-line feedback strip, where they scrolled past. It goes to the panel
now, laid out in the same three columns `help` uses.

And the panel had no **scroll bar**: it scrolled on the wheel, but a wheel is not
discoverable and a page that ends mid-sentence reads as truncated rather than
scrolled. `InternalGui._paint_info` draws a track and a thumb whenever the text
is taller than the panel, and the text column narrows to make room rather than
running underneath it.

### G. Export: `.wrl`, `.glb`, `.stl`

`.glb` (binary glTF) is the one with a stated purpose — **PowerPoint imports
it** — so it is the one to get right first. `.wrl` (VRML) and `.stl` are the
PyMOL-compatible pair. All three are scene exports, so they hang off the same
geometry the renderer already builds.
