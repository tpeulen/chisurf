# A declared UI scheme every plugin is asserted against

# Where to pick this up

**Landed 2026-08-13.** The scheme, the validators, the generated artifacts and
the suites all exist and are green (128 view specs, 38 tours). What remains is
listed under *Open* below; start there.

# The problem

Two formats are written by hand, by everyone, in every plugin:

- the **view spec** (`*.view.json`) — a tool's panel as data, built by AutoForm;
- the **guided tour** (`gui/guide.json`) — the steps that point at that panel's
  controls and wait for the user to press them.

Both loaders are forgiving, and in the same expensive way.
`chisurf.core.dataspec.load_view_spec` builds each section with
`{k: v for k, v in d.items() if k in fields}` — every key the dataclass does not
declare is **dropped without a word**. The tour loader returns an empty tour
rather than raising. So a misspelled key is not an error. It is a control that
never appears, or a step that points at nothing, discovered by a user months
later with nothing in a log to explain it.

That is not hypothetical. Declaring the scheme found nine defects already
shipped:

| Written | What happened |
| --- | --- |
| `rebuild_on_change` on three `value` sections | dropped — only `choice` implements it, and [deliberately so](#rebuild-on-change) |
| `kind: "combo"` on a `choice` | dropped — the key is `style` |
| `kind: "path"` on two `value` sections | not an implemented kind: rendered as a plain string field with **no browse button** |
| `n_col` on an `info`, `key` on an `info`, `hide_label` on a `value` | dropped |
| `target.widget` on **nine tour steps** | the loader reads `target.name`; nine steps resolved to nothing and rendered as a centred bubble pointing at no control — in a guided tour |

None of them raised anything, anywhere.

# What was decided

**The scheme is generated from the loaders, not transcribed.**
`chisurf.core.dataspec.schema.build_view_schema()` derives one branch per
registered section type, whose properties are exactly the fields its dataclass
declares. A field added to the loader is legal the moment it exists; a key the
loader would drop is not. A transcription would be a second source of truth
that drifts, which is the thing being fixed rather than a way to fix it.

The tour scheme is written out, because the tour loader reads a plain dict by
hand and there is nothing to derive from. The suite that walks all 38 shipped
tours is what keeps it honest.

**`additionalProperties` is false everywhere.** Permitting unknown keys would
validate exactly the files that are broken. Two carve-outs are named in the
scheme itself: `_comment` at any level (99 of 128 specs carry one), and
`options` on a `custom` section (forwarded verbatim to a Python factory).

**Errors dispatch on a discriminator.** Both schemes select the branch by
`type` (or, for tours, by document shape) with `if`/`then` rather than `oneOf`.
Both accept the same documents; only the dispatched form produces a readable
message. A `oneOf` failure reports that the object matched none of seventeen
alternatives and lists what each rejected, naming the wrong section type in the
one line a plugin author reads.

(#rebuild-on-change)=
**`rebuild_on_change` stays a `choice` key.** `ChoiceSection`'s docstring gives
the reason: a full rebuild is safe for a discrete mode selector and not for a
spin box or slider, where it fires mid-drag. The three specs that set it on a
count were asking for something the framework declines to do. The dead keys
were removed rather than the field added — reversing a documented decision from
inside a validation change would be the wrong way to reopen it.

# The generalisation: every reader, not every file

A scheme that only constrains *files* misses the more expensive drift, which is
a **second reader**. Two readers of one format is precisely the arrangement that
grows two dialects — one convenient, undocumented, and valid nowhere else.

chimol is the first such reader: it builds painted forms from view specs so the
desktop app and the browser run one code path. Its first draft invented
`{"type": "float", "min": 0, "max": 1}` where the real dialect is
`{"type": "value", "kind": "float", "minimum": 0, "maximum": 1}`. It read
perfectly well there and was rejected by AutoForm and by the scheme.

So the rule is: **a reader of a shared format is asserted against the scheme
from its own side.** `chimol/test/test_chimol_follows_the_scheme.py` pins that
every kind chimol claims to render is one the loader implements, every section
type it binds is a real type, and every spec it paints also loads in the Qt
loader.

# Definition of done

- [x] A generated scheme for the view spec, derived from `_SECTION_TYPES`
- [x] A scheme for the guided tour
- [x] `validate_view_spec` / `validate_guide` returning readable, located messages
- [x] Written `schemas/*.schema.json`, with a test that they match the generator
- [x] Every shipped view spec (128) and tour (38) asserted, one test per file
- [x] Negative controls: the scheme must reject each defect that had shipped
- [x] The nine shipped defects fixed
- [x] A second reader (chimol) asserted from its own side
- [x] `docs/development/ui_data_scheme.md`
- [ ] The scheme published where an editor will find it (`$schema` in the files,
      or a `settings.json` mapping) so a plugin author is told *while writing*
      rather than by CI
- [ ] `custom` section `options` validated per registered key — today the whole
      object is opaque, which is right for an arbitrary factory and too loose
      for the eight keys that have a documented shape
- [ ] The same treatment for `manifest.json`, which has a hand-written schema
      dict and a hand-written validator that only checks unknown keys
- [ ] A generator for the *other* direction: a starter `view.json` for a model,
      so the common case never has to be spelled from memory

# Open questions

- Should validation run at **load** time rather than only in the suite? It
  would catch a spec written by a user, not only one shipped by us. Against:
  the loaders are used on hot paths and jsonschema is not free. A middle
  position is validating only when a spec fails to produce the controls a
  caller expected, which is when a diagnosis is actually wanted.
- `wizard_step` entries omit `type` entirely (all nineteen shipped ones), and
  the loader injects it. The scheme therefore has to accept a typeless section
  with the union of every type's keys, which is looser than the rest. Making
  `steps` its own definition would tighten it.
