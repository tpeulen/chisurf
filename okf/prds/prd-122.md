# core/math forwarder slice

# Why

PRD-105 phase 4: one implementation per algorithm. These rows have a
shipped engine owner and no design question — each is a
measure-A/B-then-forward job, the same shape as the pile-up port.

# The job

Per row: parity A/B at current behaviour first (every previous move found
a latent bug in one of the two copies), then forward, then delete.

1. **Richardson–Lucy** — `math/linalg` + `math/optimization` (one wraps
   the other) → `tttrlib.richardson_lucy_2d`, which
   `imaging/restoration.py` already uses. **Closed 2026-09-02, by deletion
   rather than forwarding.** Both copies had zero callers anywhere in the
   tree (only the two duplicates called each other), and the named engine
   owner is not a faithful target for either: `richardson_lucy_2d`/`_3d`
   assume a translation-invariant image/PSF pair, not the arbitrary dense
   operator matrix the deleted `solve_richardson_lucy(p, u, d, max_iter)`
   accepted. There is no version of that signature that forwards
   correctly, so the register row closes by removing the dead duplicate,
   not by rewriting it into a thin wrapper nobody calls.
   `test/core/test_math_duplication_register.py` guards the deletion and
   reproduces the deleted algorithm's own math for the record, in case a
   genuine matrix-operator Richardson-Lucy is needed again.

2. **Polymer distributions** — `math/functions/rdf.py` Gaussian chain,
   SAW-ν, WLC → `imp.bff` `PolymerChain.h` kernels. **Re-verified
   2026-09-02, not actually done — this PRD's premise was wrong.**
   `gaussian_chain`, `gaussian_chain_ree`, `saw_nu`, `worm_like_chain`,
   `worm_like_chain_linker` and `ising_chain` are still full numpy/Python
   implementations in `rdf.py`; none of them import or call `IMP.bff`.
   What actually shipped (T-20260901-08 / T-20260902-01, see
   `chisurf/core/fitting/minimizer.py:855-908` and
   `test/fitting/test_graph_fit_fret.py::test_a_polymer_distribution_is_a_node_with_the_same_curve`)
   is a **second, independent** implementation on the graph side —
   `_bff.PolymerDistances`, dispatching into the real `PolymerChain.h`
   kernels — used only when a `FRETModel` subclass builds through
   `chisurf.core.fitting.minimizer.graph_objective`, parity-pinned against
   `rdf.py`'s numpy path to 1e-8 relative tolerance. Both implementations
   are live: the graph path for models that build a graph, the numpy path
   for `update_model()` and everything that does not go through the graph
   (MCMC proposals, GUI live-preview, any `FRETModel` the graph builder
   refuses). This is real progress and worth crediting, but it is not the
   phase-4 register's bar ("in-tree copies deleted") — closing it for real
   means either routing every remaining `update_model()` caller through the
   graph or making `rdf.py` genuinely call into `bff`, and per this
   sub-task's own footprint (`rdf.py`/`special.py` read-only) that
   redesign is out of scope here. Left untouched; **not** struck from the
   PRD-105 register.

3. **Decay-convolution straggler** — `models/tcspc/nusiance.py:945`'s
   `np.convolve` branch beside the tttrlib branch → `tttrlib.fconv*`.
   **Investigated 2026-09-02, not forwarded — genuine parity failure, a
   third case needing an owner decision.** `mode == "full"` convolves an
   already-computed decay array with the IRF for four live model families
   (`models/tcspc/parse/tcspc_parse.py`,
   `models/parse/tcspc/tcspc_parse.py`, `models/tcspc/distributed_acceptor.py`,
   `models/tcspc/av_decay.py`) — not a lifetime spectrum, so none of the
   `fconv*` family applies (they all take an interleaved amplitude/lifetime
   `x`, not a raw decay curve). The one generic two-array convolution
   primitive tttrlib exposes, `sconv` (already wrapped as
   `chisurf.core.fluorescence.tcspc.convolve.convolve_decay`, used
   elsewhere in this same file), computes a **different integral**: a
   trapezoidal-rule discrete convolution that half-weights the two ends of
   each partial sum, where `np.convolve(..., mode="full")` computes the
   plain rectangular one. Verified numerically
   (`test/core/test_math_duplication_register.py::test_sconv_is_not_a_drop_in_for_full_mode_np_convolve`) —
   e.g. the first nonzero output sample comes out exactly half of the
   rectangular value. Forwarding would silently move every fit built on
   those four model families, with no way to tell from the numbers alone
   that it happened. `np.convolve` is left in place;
   `test_full_mode_convolution_is_pinned` pins the current behaviour.

Staged behind owner decisions (do **not** forward until taken — the
engine values differ on purpose):

- **Bessel `i0`** (`math/functions/special.py`) — the transposed digit,
  PRD-105 decision 1. Forwarding changes every fitted WLC distribution.
  Re-confirmed 2026-09-02: `i0`'s own docstring already documents this is
  the deliberately-kept Numerical-Recipes approximation, not `scipy`'s
  exact Bessel function. Untouched.
- **`distance_between_gaussian`** — same name, different function than
  bff's (0.93 apart on the probe), PRD-105 decision 3. Untouched.

**New, not yet in PRD-105's decisions list:** the convolution straggler
above (row 3) needs the same kind of owner sign-off as `i0` and
`distance_between_gaussian` — whether the four `mode="full"` model
families should move to the physically-motivated trapezoidal integral
(`sconv`/`tttrlib`) even though it changes their fitted output, or whether
`np.convolve`'s rectangular form is the contract to keep and codify as
the deliberate exception. Either answer is a one-line forward once taken;
neither should be taken silently by whoever picks this up next.
